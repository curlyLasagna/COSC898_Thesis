\chapter{Introduction}\label{chap:intro}

\section{The Reproducibility Issue in Computer Science Education}

Software Configuration Management (SCM) has long served as a critical pillar of modern software engineering, ensuring consistency and deterministic reproducibility across development, testing, and deployment cycles~\cite{OSCodeMy2024}. In commercial software engineering, misconfigured developer machines frequently trigger the classic ``works on my machine'' syndrome, where subtle variances in operating system libraries, compiler revisions, or environment variables introduce non-deterministic bugs. Enterprise organizations systematically mitigate this friction through dedicated platform teams, standardized developer virtual machines, and automated continuous integration pipelines. In contrast, academic computer science programs operate under severe resource constraints and lack the institutional infrastructure required to maintain homogeneous client computing environments~\cite{stokerUsingVirtualMachines2013}.

In modern computer science courses, students arrive in classrooms with a highly heterogeneous array of personal devices spanning macOS, disparate Linux distributions, and Microsoft Windows~\cite{valstarUsingDevContainersStandardize2020}. Introductory and advanced courses alike demand specialized toolchains, language runtimes, software development kits (SDKs), and external libraries. Historically, instructors have relied on imperative, manual installation guides distributed during the opening weeks of the semester. This approach invariably consumes substantial lecture and laboratory hours as teaching assistants and faculty diagnose idiosyncratic system failures, operating as impromptu technical support staff rather than focusing on foundational computer science concepts. Consequently, configuration friction becomes an artificial barrier to student engagement and academic equity throughout the semester.

The degree of ``futzing'' or the tinkering of a system's state depends on a user's general expertise in their OS and the installation process. ~\cite{hollandResearchIssuesNoFutz2001}

\section{Virtualization versus Declarative Configuration: The Architectural Dilemma}

The root cause of configuration fragility lies in the imperative architecture of conventional operating system package managers. Tools such as Debian's APT, Arch Linux's Pacman, and macOS Homebrew mutate a shared global filesystem hierarchy, modifying directories such as \texttt{/usr/bin} and \texttt{/usr/lib} in place~\cite{dolstraNixSafePolicyFree}. Because packages share mutable namespaces, upgrading a library required for one course frequently breaks the dependencies of another course, producing a web of dependency conflicts. Furthermore, because imperative package managers do not preserve transactional execution histories, rolling back failed upgrades to a known working state is not feasible.

To overcome the fragility of mutable host filesystems, the software industry widely adopted containerization via Docker and Open Container Initiative (OCI) Development Containers (DevContainers)~\cite{valstarUsingDevContainersStandardize2020}. DevContainers isolate the application runtime, compiler toolchains, and editor extensions within a sandboxed Linux container, aiming to give students a consistent environment across host operating systems. Yet a locally successful configuration does not establish that the environment will work on another machine: its apparent success may depend on packages, configuration, credentials, or cached build artifacts already present on the authoring host. This distinction is especially important in educational settings, where students begin from heterogeneous and often minimally configured computers.

In contrast to conventional container workflows, purely functional package management offers an explicit, host-native model for specifying dependencies~\cite{dolstraPurelyFunctionalSystema}. The Nix package manager treats software builds as mathematical pure functions, storing every built package under a unique cryptographic hash in an immutable directory known as the Nix store (\texttt{/nix/store})~\cite{dolstraNixOSPurelyFunctional2010}. Nix Flakes standardize this model by providing a hermetic interface governed by an explicit \texttt{flake.nix} specification and a pinned \texttt{flake.lock} dependency file~\cite{duNixRescueReproducible2026a}. Through ephemeral development shells (\texttt{devShells}), students can activate a fully configured environment with a single shell invocation (\texttt{nix develop})~\cite{bandtAssessmentReproducibilityNix2025}. The explicit specification and lock file make Nix Flakes a suitable basis for testing whether an agent-generated environment can be reproduced from a clean host, rather than merely validated where it was authored.

Despite these compelling architectural advantages, Nix Flakes have faced an acute adoption chasm in educational institutions~\cite{5BuildingReproducible}. The Nix expression language is a domain-specific, lazy functional programming language that departs radically from conventional imperative scripting. For students and instructors unfamiliar with functional paradigms, deciphering Nix syntax, navigating complex attribute sets, and interpreting cryptic evaluation stack traces presents an overwhelming cognitive barrier. As a result, educational institutions often remain tethered to familiar containerized workflows despite the reproducibility benefits of declarative configuration.

\section{AI-Assisted Synthesis: Overcoming the Usability Barrier}

Recent breakthroughs in Large Language Models (LLMs) and agent harness architectures present an unprecedented opportunity to eliminate the cognitive barrier associated with declarative systems~\cite{mengAgentHarnessLarge2026}. Rather than requiring instructors and students to compose complex Nix expressions manually, an autonomous agent can ingest natural language assignment requirements or analyze unconfigured source code repositories to synthesize valid \texttt{flake.nix} configurations automatically. By abstracting the syntax and semantics of the underlying configuration language, agentic workflows can democratize access to purely functional development environments.

However, deploying off-the-shelf, general-purpose LLMs for Nix synthesis exposes critical limitations. Because the Nix expression language represents a minute fraction of public code repositories compared to ubiquitous languages such as Python or C++, general-purpose models exhibit severe package hallucination rates~\cite{ImportingPhantomsMeasuring}. When prompted to generate Nix environments, models frequently hallucinate non-existent package attribute names, reference deprecated configuration schemas, or default to imperative package installations on the host system.

To ground the agent in domain-specific best practices, our framework introduces a specialized custom agent skill named \texttt{course-flake-generator}~\cite{AgentSkills,lingAgentSkillsDataDriven2026}. The skill encapsulates modular \texttt{devShell} templates, heuristic rule sets for detecting project requirements, and automated validation routines. By loading this structured context dynamically, the agent transitions from a generic language predictor into a specialized Nix configuration engineer capable of maintaining consistent behavioral patterns across diverse assignment prompts.

To eliminate package hallucination entirely, the agent is coupled with a dedicated Model Context Protocol (MCP) server, \texttt{mcp-nixos}~\cite{borkLanguageServerProtocol2023}. The MCP server connects the agent harness directly to the real-time Elasticsearch index powering \texttt{search.nixos.org}, enabling live verification of package attributes across the 139,000+ packages in the Nixpkgs registry. Furthermore, our pipeline exploits the deterministic nature of Nix evaluation: when a generated flake contains syntax or typing errors, the compiler diagnostics from \texttt{nix flake check} are captured and fed back into the agent harness in a closed-loop recovery cycle, allowing the agent to self-correct invalid declarations prior to student deployment.

\section{Research Objectives and Contributions}

This thesis addresses the fundamental tension between reproducibility and usability in educational development environments. By automating the synthesis and validation of Nix Flakes through an agentic AI pipeline, we examine whether educational institutions can obtain reproducible, host-native development environments without subjecting students or instructors to the steep learning curve of nix.

To formalize this investigation, this research pursues three primary Research Questions:
\begin{enumerate}
	\item \textbf{RQ1 (Agentic Synthesis Accuracy):} Can an AI agent accurately infer system-level dependencies from natural language assignment instructions or unconfigured source code to automatically generate valid, reproducible \texttt{flake.nix} environments?
	\item \textbf{RQ2 (Clean-Container Reproducibility):} To what extent do Nix Flake environments that pass local validation reproduce and support headless coursework tasks in a fresh Linux container without the authoring machine's files, configuration, or prior evaluation state?
	\item \textbf{RQ3 (Classroom Deployment Reliability):} To what extent can Nix Flake environments provide a dependable foundation for classroom use, and what operational constraints and risk trade-offs shape that dependability?
\end{enumerate}

In answering these questions, this thesis makes the following concrete contributions:
\begin{enumerate}
	\item We present an end-to-end automated synthesis pipeline that translates natural language course assignment descriptions and unconfigured codebases into hermetic, multi-architecture \texttt{flake.nix} specifications.
	\item We design and implement a custom agent skill that instructs the agent to  query official Nixpkgs search indices in real time, eliminating package hallucinations in generated environment files.
	\item We provide a clean-container replay evaluation that runs every stage for each RQ1-passing flake in a fresh, unmounted Nix Docker container, then measures successful evaluation, development-shell activation, required executable availability, and curated headless coursework-task execution.
	\item We identify and evaluate the operational conditions that affect classroom reliability: locked-input availability, package maintenance, binary-cache coverage and source-build fallback, and the trust boundary introduced by additional substituters.
\end{enumerate}
