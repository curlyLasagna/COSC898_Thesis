\chapter{Introduction}\label{chap:intro}

\section{The Reproducibility Issue in Computer Science Education Luis was here}

Software Configuration Management continues to be a critical component of modern software engineering, ensuring consistency and deterministic reproducibility across development, testing, and deployment cycles~\cite{dolstraNixSafePolicyFree,functionalSoftware,OSCodeMy2024}. In commercial software engineering, misconfigured developer machines frequently trigger the classic ``works on my machine'' syndrome, where subtle variances in operating system libraries, compiler revisions, or environment variables introduce non-deterministic bugs. Enterprise organizations systematically mitigate this friction through dedicated platform teams, standardized developer virtual machines, and automated continuous integration pipelines. In contrast, academic computer science programs either expect students to install and configure the required toolchains on their own, or provide pre-configured centralized servers, virtual machines, or containers that each introduce distinct operational and resource trade-offs~\cite{stokerUsingVirtualMachines2013,valstarUsingDevContainersStandardize2020,malanContainerizingCS50Standardizing2024}.

In modern computer science courses, students arrive in classrooms with a highly heterogeneous array of personal devices spanning macOS, disparate Linux distributions, and Microsoft Windows~\cite{valstarUsingDevContainersStandardize2020,malanContainerizingCS50Standardizing2024}. Introductory and advanced courses alike demand specialized toolchains, language runtimes, software development kits (SDKs), and external libraries. Historically, instructors have relied on imperative, manual installation guides distributed during the opening weeks of the semester~\cite{valstarUsingDevContainersStandardize2020,harvieUsingVirtualMachines2019}. This approach invariably consumes substantial lecture and laboratory hours as teaching assistants and faculty diagnose idiosyncratic system failures, operating as impromptu technical support staff rather than focusing on foundational computer science concepts~\cite{valstarUsingDevContainersStandardize2020,malanContainerizingCS50Standardizing2024}.

Holland et~al.~\cite{hollandResearchIssuesNoFutz2001} characterize this manual tinkering with a system's state as ``futzing,'' demonstrating that manual configuration state and mutable operating system or application file state are primary sources of system fragility where minor misconfigurations or conflicting installations can render software components completely inoperative. Because the burden of futzing depends heavily on a user's prior operating system expertise, novice students frequently lack the system administration experience required to recover from environmental failures~\cite{hollandResearchIssuesNoFutz2001,harvieUsingVirtualMachines2019}, transforming configuration friction into an artificial barrier to student engagement and academic equity throughout the semester.

\section{Virtualization versus Declarative Configuration: The Architectural Dilemma}

The root cause of configuration fragility lies in the imperative architecture of conventional graphical installers and package managers. Tools such as Debian's \texttt{apt}, Arch's \texttt{pacman}, and macOS \texttt{brew} destructively mutate a shared global filesystem hierarchy, overwriting files in directories such as \texttt{/usr/bin} and \texttt{/usr/lib} in place~\cite{dolstraNixSafePolicyFree,duNixRescueReproducible2026a}. Because packages share mutable namespaces, upgrading a library required for one course frequently breaks the dependencies of another course, producing a web of dependency conflicts~\cite{dolstraNixSafePolicyFree,hollandResearchIssuesNoFutz2001}. Furthermore, because imperative package managers do not support atomic upgrades or preserve transactional execution histories, rolling back failed upgrades to a known working state is rarely feasible without full reinstallation~\cite{dolstraNixSafePolicyFree,hollandResearchIssuesNoFutz2001}.

To overcome the fragility of mutable host filesystems, the software industry and computer science educators widely adopted containerization via Docker and Open Container Initiative (OCI) Development Containers (DevContainers)~\cite{valstarUsingDevContainersStandardize2020,malanContainerizingCS50Standardizing2024}. DevContainers isolate the application runtime, compiler toolchains, and editor extensions within a sandboxed Linux container, aiming to give students a consistent environment across host operating systems~\cite{valstarUsingDevContainersStandardize2020}. However, container images built via imperative \texttt{Dockerfile} instructions still suffer from unpinned upstream package layers and impose heavy background virtualization overhead on macOS and Windows hosts~\cite{valstarUsingDevContainersStandardize2020,duNixRescueReproducible2026a,NixBetterDocker2024}. Moreover, a locally successful configuration does not establish that an environment will work on another machine: its apparent success may depend on packages, configuration, credentials, or cached build artifacts already present on the authoring host.

In contrast to conventional container workflows, purely functional package management offers an explicit, host-native model for specifying dependencies~\cite{dolstraPurelyFunctionalSystema,functionalSoftware}. The Nix package manager treats software builds as pure functions of their declared inputs, storing every built package under a unique cryptographic hash in an immutable directory known as the Nix store (\texttt{/nix/store})~\cite{dolstraNixSafePolicyFree,dolstraNixOSPurelyFunctional2010}. Nix Flakes standardize this model by providing a hermetic interface governed by a \texttt{flake.nix} specification and a pinned \texttt{flake.lock} dependency file, which empirical studies have shown to support high build reproducibility across time and platforms~\cite{duNixRescueReproducible2026a,bandtAssessmentReproducibilityNix2025,malkaReproducibilityBuildEnvironments2024}. Through ephemeral development shells (\texttt{devShells}), students can activate a fully configured environment with a single shell invocation (\texttt{nix develop}) and deactivate the same development shell without incurring side effects on their host system~\cite{5BuildingReproducible,duNixRescueReproducible2026a}. The explicit specification and lock file make Nix Flakes a suitable basis for testing whether an agent-generated environment can be reproduced from a clean host, rather than merely validated where it was authored.

Chapter~\ref{chap:litreview} provides the technical background on Nix and how it stacks against its alternatives. It reviews existing approaches to educational environment management, identifies their operational bottlenecks, and establishes the foundational concepts of functional package management.

Despite these compelling architectural advantages, Nix Flakes have faced an acute adoption chasm in educational institutions~\cite{5BuildingReproducible,duNixRescueReproducible2026a}. The Nix expression language is a domain-specific, lazy functional programming language that departs radically from conventional imperative scripting~\cite{ModularityLazyEvaluation,duNixRescueReproducible2026a}. For students and instructors unfamiliar with functional paradigms, deciphering Nix syntax, working around isolated \texttt{/nix/store} conventions, and interpreting cryptic evaluation stack traces presents an overwhelming cognitive barrier~\cite{duNixRescueReproducible2026a,hauschImprovingReproducibilityScientific2025,OSCodeMy2024}. As a result, educational institutions often remain tethered to familiar imperative workflows despite the reproducibility benefits of declarative configuration.

\section{AI-Assisted Synthesis: Overcoming the Usability Barrier}

Recent breakthroughs in Large Language Models (LLMs) and agent harness architectures present an unprecedented opportunity to lower the cognitive barrier associated with declarative systems~\cite{mengAgentHarnessLarge2026,formentScaffoldingMattersMore2026,duNixRescueReproducible2026a}. Rather than requiring instructors and students to compose complex Nix expressions manually, an autonomous agent can ingest natural language assignment requirements or analyze unconfigured source code repositories to synthesize valid \texttt{flake.nix} configurations automatically. By abstracting the syntax and semantics of the underlying configuration language, agentic workflows can democratize access to purely functional development environments.

However, deploying off-the-shelf, general-purpose LLMs for generating Nix Flake files exposes critical limitations. Recent benchmarks on automated Infrastructure as Code (IaC) synthesis show that state-of-the-art LLMs achieve low first-attempt pass and deployability rates when generating declarative configurations without iterative verification~\cite{konIaCEvalCodeGeneration,zhangDeployabilityCentricInfrastructureasCodeGeneration2025}. Furthermore, because the Nix expression language represents a small fraction of public training corpora compared to ubiquitous languages such as Python or JavaScript, general-purpose models are vulnerable to severe package hallucination rates~\cite{ImportingPhantomsMeasuring,srivatsaSurveyUsingLarge}. When prompted to generate Nix environments, unassisted models frequently hallucinate non-existent package attribute names, reference deprecated configuration schemas, or default to imperative package installations on the host system.

To ground the agent in domain-specific best practices, our framework introduces a specialized custom agent skill named \texttt{course-flake-generator}~\cite{AgentSkills,lingAgentSkillsDataDriven2026}. The skill provides \texttt{flake.nix} templates, heuristic rule sets for detecting project requirements, and automated validation routines. By loading this structured procedural context dynamically within the agent harness~\cite{mengAgentHarnessLarge2026,lingAgentSkillsDataDriven2026}, the agent transitions from a generic language predictor into a specialized Nix configuration engineer capable of maintaining consistent behavioral patterns across diverse assignment prompts.

To mitigate package hallucination, the agent is coupled with a dedicated Model Context Protocol (MCP)~\cite{MCPLandscape} server, \texttt{mcp-nixos}, which follows the architectural decoupling popularized by the Language Server Protocol (LSP)~\cite{borkLanguageServerProtocol2023}. The MCP server connects the agent harness directly to the real-time Elasticsearch index powering \texttt{search.nixos.org}, enabling live verification of package attributes across the 139,000+ packages in the Nixpkgs registry. Furthermore, our pipeline exploits the deterministic nature of Nix evaluation: when a generated flake contains syntax or typing errors, the compiler diagnostics from \texttt{nix flake check} are captured and fed back into the agent harness in a closed-loop recovery cycle~\cite{zhangDeployabilityCentricInfrastructureasCodeGeneration2025,mengAgentHarnessLarge2026}, allowing the agent to self-correct invalid declarations prior to student deployment.

\section{Research Objectives and Contributions}

This thesis addresses the fundamental tension between reproducibility and usability in educational development environments. By automating the synthesis and validation of Nix Flakes through an agentic AI pipeline, we examine whether educational institutions can obtain reproducible, host-native development environments without subjecting students or instructors to the steep learning curve of Nix.

To formalize this investigation, this research pursues three primary Research Questions:
\rqlist

In answering these questions, this thesis makes the following concrete contributions:
\begin{enumerate}
	\item We present an end-to-end automated synthesis pipeline that translates natural language course assignment descriptions, instructional documents and unconfigured codebases into multi-architecture \texttt{flake.nix} specifications.
	\item We design and implement a custom agent skill that instructs the agent to query official Nixpkgs search indices in real time, eliminating package hallucinations in generated environment files.
	\item We provide a base OS replay evaluation that runs every stage for each RQ1-passing flake in a fresh, unmounted Nix Docker container, then measures successful evaluation, development-shell activation, required executable availability, and curated headless coursework-task execution.
	\item We evaluate student onboarding ergonomics by comparing setup time deltas and cognitive friction between traditional imperative installation instructions and single-command environment activation via \texttt{nix develop}, alongside an analysis of the theoretical operational constraints governing classroom deployment.
\end{enumerate}

The remainder of this thesis is organized as follows. Finally, Chapter~\ref{conclusion} summarizes the findings of this thesis and highlights promising avenues for future research.
