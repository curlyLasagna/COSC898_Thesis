\chapter{Introduction}\label{chap:intro}

\section{The Reproducibility Crisis in Computer Science Education}

Software Configuration Management (SCM) has long served as a critical pillar of modern software engineering, ensuring consistency and deterministic reproducibility across development, testing, and deployment cycles~\cite{OSCodeMy2024}. In commercial software engineering, misconfigured developer machines frequently trigger the classic ``works on my machine'' syndrome, where subtle variances in operating system libraries, compiler revisions, or environment variables introduce non-deterministic bugs. Enterprise organizations systematically mitigate this friction through dedicated platform teams, standardized developer virtual machines, and automated continuous integration pipelines. In contrast, academic computer science programs operate under severe resource constraints and lack the institutional infrastructure required to maintain homogeneous client computing environments~\cite{stokerUsingVirtualMachines2013}.

In modern computer science courses, students arrive in classrooms with a highly heterogeneous array of personal devices spanning macOS, disparate Linux distributions, and Microsoft Windows~\cite{valstarUsingDevContainersStandardize2020}. Introductory and advanced courses alike demand specialized toolchains, language runtimes, software development kits (SDKs), and external libraries. Historically, instructors have relied on imperative, manual installation guides distributed during the opening weeks of the semester. This approach invariably consumes substantial lecture and laboratory hours as teaching assistants and faculty diagnose idiosyncratic system failures, operating as impromptu technical support staff rather than focusing on foundational computer science concepts. Consequently, configuration friction becomes an artificial barrier to student engagement and academic equity.

\section{Virtualization versus Declarative Configuration: The Architectural Dilemma}

The root cause of configuration fragility lies in the imperative architecture of conventional operating system package managers. Tools such as Debian's APT, Arch Linux's Pacman, and macOS Homebrew mutate a shared global filesystem hierarchy, modifying directories such as \texttt{/usr/bin} and \texttt{/usr/lib} in place~\cite{dolstraNixSafePolicyFree}. Because packages share mutable namespaces, upgrading a library required for one course frequently breaks the dependencies of another course, producing intractable dependency conflicts. Furthermore, because imperative package managers do not preserve transactional execution histories, rolling back failed upgrades to a known working state is extraordinarily difficult.

To overcome the fragility of mutable host filesystems, the software industry widely adopted containerization via Docker and Open Container Initiative (OCI) Development Containers (DevContainers)~\cite{valstarUsingDevContainersStandardize2020}. DevContainers isolate the application runtime, compiler toolchains, and editor extensions within a sandboxed Linux container, ensuring that students execute assignments in an identical environment regardless of host operating system. However, this isolation comes at a steep computational cost on consumer hardware. On non-Linux platforms such as macOS and Windows, containers require a background Linux virtual machine hypervisor, which persistently consumes between 1.8~GB and 2.4~GB of idle random-access memory (RAM)~\cite{NixBetterDocker2024}. In the wake of global memory supply shortages and surging semiconductor prices, such heavy memory footprints strain student laptops, causing sluggish performance and thermal throttling when running concurrently with modern development environments and web browsers~\cite{2025PresentGlobal2026}. Additionally, container images duplicate common base layers across multiple courses, resulting in severe disk bloat.

In contrast to process virtualization, purely functional package management offers a lightweight, host-native alternative~\cite{dolstraPurelyFunctionalSystema}. The Nix package manager treats software builds as mathematical pure functions, storing every built package under a unique cryptographic hash in an immutable directory known as the Nix store (\texttt{/nix/store})~\cite{dolstraNixOSPurelyFunctional2010}. Nix Flakes standardize this model by providing a hermetic interface governed by an explicit \texttt{flake.nix} specification and a pinned \texttt{flake.lock} dependency file~\cite{duNixRescueReproducible2026}. Through ephemeral development shells (\texttt{devShells}), students can activate a fully configured, isolated development environment with a single shell invocation (\texttt{nix develop}), incurring zero hypervisor memory overhead while executing natively on the host kernel~\cite{bandtAssessmentReproducibilityNix2025}.

Despite these compelling architectural advantages, Nix Flakes have faced an acute adoption chasm in educational institutions~\cite{5BuildingReproducible}. The Nix expression language is a domain-specific, lazy functional programming language that departs radically from conventional imperative scripting. For students and instructors unfamiliar with functional paradigms, deciphering Nix syntax, navigating complex attribute sets, and interpreting cryptic evaluation stack traces presents an overwhelming cognitive barrier. As a result, educational institutions often remain tethered to resource-heavy containerized workflows despite their recognized performance deficiencies.

\section{AI-Assisted Synthesis: Overcoming the Usability Barrier}

Recent breakthroughs in Large Language Models (LLMs) and agent harness architectures present an unprecedented opportunity to eliminate the cognitive barrier associated with declarative systems~\cite{mengAgentHarnessLarge2026}. Rather than requiring instructors and students to compose complex Nix expressions manually, an autonomous agent can ingest natural language assignment requirements or analyze unconfigured source code repositories to synthesize valid \texttt{flake.nix} configurations automatically. By abstracting the syntax and semantics of the underlying configuration language, agentic workflows can democratize access to purely functional development environments.

However, deploying off-the-shelf, general-purpose LLMs for Nix synthesis exposes critical limitations. Because the Nix expression language represents a minute fraction of public code repositories compared to ubiquitous languages such as Python or C++, general-purpose models exhibit severe package hallucination rates~\cite{ImportingPhantomsMeasuring}. When prompted to generate Nix environments, models frequently hallucinate non-existent package attribute names, reference deprecated configuration schemas, or default to imperative package installations on the host system.

To ground the agent in domain-specific best practices, our framework introduces a specialized custom agent skill named \texttt{course-flake-generator}~\cite{AgentSkills,lingAgentSkillsDataDriven2026}. The skill encapsulates modular \texttt{devShell} templates, heuristic rule sets for detecting project requirements, and automated validation routines. By loading this structured context dynamically, the agent transitions from a generic language predictor into a specialized Nix configuration engineer capable of maintaining consistent behavioral patterns across diverse assignment prompts.

To eliminate package hallucination entirely, the agent is coupled with a dedicated Model Context Protocol (MCP) server, \texttt{mcp-nixos}~\cite{borkLanguageServerProtocol2023}. The MCP server connects the agent harness directly to the real-time Elasticsearch index powering \texttt{search.nixos.org}, enabling live verification of package attributes across the 139,000+ packages in the Nixpkgs registry. Furthermore, our pipeline exploits the deterministic nature of Nix evaluation: when a generated flake contains syntax or typing errors, the compiler diagnostics from \texttt{nix flake check} are captured and fed back into the agent harness in a closed-loop recovery cycle, allowing the agent to self-correct invalid declarations prior to student deployment.

\section{Research Objectives and Contributions}

This thesis addresses the fundamental tension between computational efficiency and usability in educational development environments. By automating the synthesis and validation of Nix Flakes through an agentic AI pipeline, we demonstrate that educational institutions can achieve lightweight, host-native reproducibility without subjecting students or instructors to the steep learning curve of functional package management.

To formalize this investigation, this research pursues three primary Research Questions:
\begin{enumerate}
    \item \textbf{RQ1 (Agentic Synthesis Accuracy):} Can an AI agent accurately infer system-level dependencies from natural language assignment instructions or unconfigured source code to automatically generate valid, reproducible \texttt{flake.nix} environments?
    \item \textbf{RQ2 (Computational Footprint Comparison):} How do the computational footprints---specifically memory overhead, disk deduplication across heterogeneous course suites, and cold-start activation latency---of Nix Flakes and OCI DevContainers compare against native host baselines?
    \item \textbf{RQ3 (Pedagogical and Adoption Barriers):} While containerization and declarative environments have theoretically resolved the ``works on my machine'' dilemma in industrial software engineering, what technical, cognitive, and organizational factors continue to hinder their adoption in university classrooms?
\end{enumerate}

In answering these questions, this thesis makes the following concrete contributions:
\begin{enumerate}
    \item We present an end-to-end automated synthesis pipeline that translates natural language course assignment descriptions and unconfigured codebases into hermetic, multi-architecture \texttt{flake.nix} specifications.
    \item We design and implement a custom agent skill and an \texttt{mcp-nixos} retrieval server that queries official Nixpkgs search indices in real time, virtually eliminating package hallucinations in generated environment files.
    \item We construct a closed-loop deterministic validation mechanism that leverages compiler stack traces from native Nix evaluation commands to enable autonomous agent error diagnosis and self-correction.
    \item We provide a comprehensive empirical benchmark on consumer laptop hardware comparing Nix Flakes, OCI DevContainers, and native host baselines across resident memory consumption, multi-course disk deduplication, and cold-start activation latency.
\end{enumerate}
