\chapter{Introduction}\label{chap:intro}

\section{The Environment Configuration Problem in Computer Science Education}

In computer science education, programming assignments are designed to teach algorithmic thinking, systems design, and domain-specific problem solving; yet in practice, students frequently spend a disproportionate share of their assignment time configuring development environments rather than writing code~\cite{valstarUsingDevContainersStandardize2020,harvieUsingVirtualMachines2019,malanContainerizingCS50Standardizing2024}. Modern university classrooms encompass a highly heterogeneous array of personal student laptops spanning macOS, disparate Linux distributions, and Microsoft Windows~\cite{valstarUsingDevContainersStandardize2020,malanContainerizingCS50Standardizing2024}. Because introductory and advanced courses alike depend on specialized compilers, language runtimes, software development kits (SDKs), and native libraries, minor variations across student operating systems routinely trigger installation failures, path misconfigurations, and library version conflicts before a student can begin the actual coursework.

For instructors and teaching assistants, this operating system diversity creates an acute support burden. Historically, course staff have relied on imperative, step-by-step installation guides distributed at the start of a semester or alongside individual assignments~\cite{valstarUsingDevContainersStandardize2020,harvieUsingVirtualMachines2019}. When these manual instructions encounter preexisting packages, non-standard shell profiles, or operating system updates on student machines, lecture periods, laboratory sessions, and office hours are diverted from computer science pedagogy into ad-hoc technical support~\cite{valstarUsingDevContainersStandardize2020,malanContainerizingCS50Standardizing2024}. Commercial software engineering organizations mitigate this friction through dedicated platform engineering teams, standardized corporate hardware, and managed developer images~\cite{dolstraNixSafePolicyFree,functionalSoftware,OSCodeMy2024}. In contrast, academic instructors must support students working on unmanaged personal devices with widely varying system configurations.

Holland et~al.~\cite{hollandResearchIssuesNoFutz2001} characterize this manual, trial-and-error tinkering with system state as ``futzing,'' showing that mutable operating system and application state is a primary source of software fragility in which a single misordered command or conflicting package installation can leave a machine in a broken intermediate state. Because recovering from such failures requires system administration expertise that students are still developing~\cite{hollandResearchIssuesNoFutz2001,harvieUsingVirtualMachines2019}, environment configuration friction acts as an unproductive barrier that consumes student time, delays assignment progress, and undermines equitable participation across the curriculum.

\section{Virtualization versus Declarative Configuration}

The root cause of configuration fragility lies in the imperative architecture of conventional graphical installers and package managers. Tools such as Debian's \texttt{apt}, Arch's \texttt{pacman}, and macOS \texttt{brew} destructively mutate a shared global filesystem hierarchy, overwriting files in directories such as \texttt{/usr/bin} and \texttt{/usr/lib} in place~\cite{dolstraNixSafePolicyFree,duNixRescueReproducible2026a}. Because packages share mutable namespaces, upgrading a library required for one course frequently breaks the dependencies of another course, producing a web of dependency conflicts~\cite{dolstraNixSafePolicyFree,hollandResearchIssuesNoFutz2001}. Furthermore, because imperative package managers do not support atomic upgrades or preserve transactional execution histories, rolling back failed upgrades to a known working state is rarely feasible without full reinstallation~\cite{dolstraNixSafePolicyFree,hollandResearchIssuesNoFutz2001}.

To overcome the fragility of mutable host filesystems, the software industry and computer science educators widely adopted containerization via Docker and Open Container Initiative (OCI) Development Containers (DevContainers)~\cite{valstarUsingDevContainersStandardize2020,malanContainerizingCS50Standardizing2024}. DevContainers isolate the application runtime, compiler toolchains, and editor extensions within a sandboxed Linux container, aiming to give students a consistent environment across host operating systems~\cite{valstarUsingDevContainersStandardize2020}. However, container images built via imperative \texttt{Dockerfile} instructions still suffer from unpinned upstream package layers and impose heavy background virtualization overhead on macOS and Windows hosts~\cite{valstarUsingDevContainersStandardize2020,duNixRescueReproducible2026a,NixBetterDocker2024}. Moreover, a locally successful configuration does not establish that an environment will work on another machine: its apparent success may depend on packages, configuration, credentials, or cached build artifacts already present on the authoring host.

In contrast to conventional container workflows, purely functional package management offers an explicit, host-native model for specifying dependencies~\cite{dolstraPurelyFunctionalSystema,functionalSoftware}. The Nix package manager treats software builds as pure functions of their declared inputs, storing every built package under a unique cryptographic hash in an immutable directory known as the Nix store (\texttt{/nix/store})~\cite{dolstraNixSafePolicyFree,dolstraNixOSPurelyFunctional2010}. Nix Flakes standardize this model by providing a hermetic interface governed by a \texttt{flake.nix} specification and a pinned \texttt{flake.lock} dependency file, which empirical studies have shown to support high build reproducibility across time and platforms~\cite{duNixRescueReproducible2026a,bandtAssessmentReproducibilityNix2025,malkaReproducibilityBuildEnvironments2024}. Through ephemeral development shells (\texttt{devShells}), students can activate a fully configured environment with a single shell invocation (\texttt{nix develop}) and deactivate the same development shell without incurring side effects on their host system~\cite{5BuildingReproducible,duNixRescueReproducible2026a}. This isolation is especially beneficial for students enrolled concurrently in multiple computer science courses with differing or conflicting technical requirements. Rather than downloading and managing disparate applications, database servers, and runtime version managers that risk clashing on the global filesystem, students need only install Nix once. The flake file associated with each course repository cleanly isolates and manages all required dependencies, allowing students to switch between course environments without cross-course interference. The explicit specification and lock file also make Nix Flakes a suitable basis for testing whether an agent-generated environment can be reproduced from a clean host, rather than merely validated where it was authored.

Chapter~\ref{chap:litreview} provides the technical background on Nix and how it stacks against its alternatives. It reviews existing approaches to educational environment management, identifies their operational bottlenecks, and establishes the foundational concepts of functional package management.

Despite these compelling architectural advantages, Nix Flakes have faced an acute adoption chasm in educational institutions~\cite{5BuildingReproducible,duNixRescueReproducible2026a}. The Nix expression language is a domain-specific, lazy functional programming language that departs radically from conventional imperative scripting~\cite{ModularityLazyEvaluation,duNixRescueReproducible2026a}. Expecting instructors to manually author and maintain multi-architecture \texttt{flake.nix} specifications for every course assignment, or expecting students to diagnose cryptic Nix evaluation traces, merely trades one form of configuration burden for another~\cite{duNixRescueReproducible2026a,hauschImprovingReproducibilityScientific2025,OSCodeMy2024}. Consequently, instructors remain tethered to fragile manual installation guides or container workflows that demand background Linux virtual machines and substantial memory overhead on non-Linux laptops.

\section{Proposed Approach: An Agent Skill for Assignment-to-Flake Synthesis}

What if an instructor could simply provide an existing assignment document to an AI agent that automatically extracts requirements, generates a reproducible development environment, and verifies its validity? The instructor could then review and distribute that verified configuration to the class, allowing students to activate a fully provisioned development environment through a single text file (\texttt{flake.nix}) and a single command-line invocation (\texttt{nix develop}) rather than manual imperative setup.

This thesis realizes that vision through \texttt{course-flake-generator}, a custom agent skill that enables instructors to transform existing course materials into ready-to-use Nix Flake development environments using their own local AI agent harness~\cite{mengAgentHarnessLarge2026,formentScaffoldingMattersMore2026,duNixRescueReproducible2026a}. Rather than requiring instructors or students to master the Nix expression language, the skill equips the instructor's local agent harness to execute a structured assignment-to-flake workflow spanning requirement extraction, flake generation, closed-loop compiler validation, instructor approval, and student activation.

First, the workflow begins with an instructor's existing assignment materials, such as a PDF, Microsoft Word handout, a README.md file, or unconfigured starter codebase. Second, the custom agent skill provides extraction scripts and heuristics that inspect the assignment materials and scan project manifests to infer required compilers, language runtimes, build tools, and libraries. Third, the skill guides the agent using curated multi-architecture templates to synthesize a declarative \texttt{flake.nix} specification tailored to the assignment. Fourth, the candidate flake undergoes automated validation, where skill-bundled validation routines execute closed-loop evaluation and shell realization checks to catch syntax errors or missing dependencies and produce a cryptographically pinned \texttt{flake.lock} file. Fifth, the instructor reviews the verified configuration and commits it to the assignment repository. Finally, students clone or download the repository onto their personal machines and invoke a single command (\texttt{nix develop}) to enter a reproducible development shell and immediately begin working on the assignment.

This workflow is especially advantageous for instructors managing semester-long courses. Instead of maintaining per-platform setup scripts or fielding repetitive installation guides, instructors can distribute a single, self-contained configuration file alongside their assignment repository. Teaching assistants and lab instructors are thereby freed from manual troubleshooting, allowing course staff to dedicate their office hours to algorithmic guidance and conceptual assistance.

Deploying off-the-shelf Large Language Models (LLMs) without specialized scaffolding exposes critical limitations for environment generation. Recent benchmarks on automated Infrastructure as Code (IaC) synthesis show that general-purpose LLMs achieve low first-attempt pass and deployability rates when generating declarative configurations without iterative verification~\cite{konIaCEvalCodeGeneration,zhangDeployabilityCentricInfrastructureasCodeGeneration2025}. Furthermore, because the Nix expression language represents a small fraction of public training corpora compared to ubiquitous languages such as Python or JavaScript, unassisted models suffer from elevated package hallucination rates~\cite{ImportingPhantomsMeasuring,srivatsaSurveyUsingLarge}. Unassisted models frequently fabricate non-existent Nixpkgs attribute names, reference deprecated configuration schemas, or default to imperative host installation commands (such as \texttt{brew install}) that defeat cross-platform reproducibility.

To address these vulnerabilities, our \texttt{course-flake-generator} skill packages domain-specific procedural knowledge into an open, modular format consisting of structured instructions (\texttt{SKILL.md}), multi-architecture templates, and helper scripts~\cite{AgentSkills,lingAgentSkillsDataDriven2026}. By loading this procedural context dynamically within the instructor's local agent harness~\cite{mengAgentHarnessLarge2026,lingAgentSkillsDataDriven2026}, the agent reliably extracts requirements and generates valid declarative environments.

To resolve and verify package attributes deterministically during flake generation, the skill's primary package discovery mechanism queries a dedicated Model Context Protocol (MCP)~\cite{MCPLandscape} server, \texttt{mcp-nixos}, which connects directly to the real-time Elasticsearch index powering \texttt{search.nixos.org}. When the MCP server is unavailable or disabled, the skill provides a fallback procedure using native Nix CLI inspection tools (such as \texttt{nix search} and \texttt{nix eval}). Crucially, rather than relying on package search alone, the workflow exploits the deterministic nature of Nix evaluation: when a generated flake contains syntax or typing errors, compiler diagnostics from \texttt{nix flake check} and \texttt{nix develop} are captured and fed back into the agent harness in a closed-loop recovery cycle~\cite{zhangDeployabilityCentricInfrastructureasCodeGeneration2025,mengAgentHarnessLarge2026}. This feedback loop allows the agent to iteratively self-correct invalid declarations prior to finalizing the generated flake.

\section{Research Objectives and Contributions}

The primary objective of this thesis is to eliminate the unproductive time students spend configuring local development environments and to alleviate the burden instructors face in supporting diverse student machines. By equipping an instructor's AI agent harness with a custom agent skill to synthesize validated, instructor-approved Nix Flake environments directly from assignment materials, we investigate whether computer science courses can achieve deterministic, cross-platform environment reproducibility while providing students with a frictionless, single-command onboarding experience.

To evaluate each phase of the proposed assignment-to-flake workflow (from agentic requirement extraction and generation in Stages~1--4, to cross-platform portability of the instructor-approved environment in Stage~5, to student activation in practice in Stage~6), this research pursues three primary research questions. These questions systematically investigate synthesis reliability, cross-platform reproduction fidelity, and student onboarding ergonomics:
\rqlist

In answering these questions, this thesis makes four concrete contributions to computer science education and automated environment synthesis. Together, these contributions bridge the gap between declarative package management and practical classroom deployment:
\begin{enumerate}
	\item We design and implement \texttt{course-flake-generator} (\url{https://github.com/curlyLasagna/Thesis-Flake-Generator}), an open-standard agent skill that equips an instructor's AI agent harness to extract software requirements from assignment documents and existing codebases, generate \texttt{flake.nix} files, validate them in a closed loop, and produce pinned \texttt{flake.lock} files ready for classroom distribution.
	\item Across a two-track computer science curriculum benchmark (Software Development and Data Science), we evaluate how procedural skill scaffolding, closed-loop compiler verification, and package discovery strategies (evaluating the primary \texttt{mcp-nixos} registry server alongside a native Nix CLI fallback condition) influence synthesis accuracy (Pass@$k$), package precision, and dependency over-provisioning across frontier and open-weight models.
	\item We develop a script to automate tests of the generated flakes across fresh, unmounted Linux containers and macOS virtual machines, quantifying cross-platform reproduction rates and exposing hidden authoring-host assumptions before environments reach student laptops.
	\item Through a controlled onboarding study on clean virtual machines, we compare single-command student activation (\texttt{nix develop}) against manual installation from assignment guides in terms of setup time deltas, procedural error prevention, and cognitive friction, complemented by an operational and security analysis of classroom deployment.
\end{enumerate}
