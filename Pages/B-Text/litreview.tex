\chapter{Background and Literature Review}\label{chap:litreview}

\section{Related Work}\label{sec:related-work}

\subsection{Standardizing Educational Environments via Virtual Machines and Containers}

Standardizing student development environments has remained a persistent pedagogical challenge in computer science education~\cite{stokerUsingVirtualMachines2013,harvieUsingVirtualMachines2019}. In traditional coursework, students frequently encounter installation failures, library mismatches, and operating system incompatibilities when attempting to manually configure personal machines for laboratory assignments. Installation failures may hinder a student's drive to continue learning, consuming significant classroom troubleshooting time and potentially leading less experienced students to conclude that programming is not for them before writing a single line of code~\cite{harvieUsingVirtualMachines2019,malanContainerizingCS50Standardizing2024}.

Historically, institutions attempted to resolve configuration discrepancies by deploying centralized compute clusters or multi-user Linux servers accessible via SSH or remote desktop protocols~\cite{malanContainerizingCS50Standardizing2024}. Both Valstar et~al.~\cite{valstarUsingDevContainersStandardize2020} and Malan~\cite{malanContainerizingCS50Standardizing2024} critically analyze the friction inherent in these pre-configured central servers, noting that because instructors lack administrative privileges to install applications, they must continually coordinate with central IT personnel who manage infrastructure across disparate academic departments. To bypass these restrictions, Malan~\cite{malanContainerizingCS50Standardizing2024} notes that instructors often had to resort to compiling programs from source into shared course directories. This administrative bottleneck results in sluggish response times when course toolchains require updates during active semesters, with Valstar et~al.~\cite{valstarUsingDevContainersStandardize2020} observing multi-week reconfiguration delays that left laboratory software versions up to five years out of date.

Furthermore, centralized remote architectures impose rigid network requirements~\cite{valstarUsingDevContainersStandardize2020}. Students must maintain persistent, low-latency network connections, either on campus or through remote SSH sessions. Unstable internet connections introduce substantial input latency and unexpected disconnects, especially near assignment deadlines, severely disrupting the student learning experience during programming assignments and interactive debugging sessions~\cite{valstarUsingDevContainersStandardize2020}. To alleviate these network and administrative dependencies, educators started incorporating virtual machines into their courses~\cite{harvieUsingVirtualMachines2019,stokerUsingVirtualMachines2013}. Virtual machines provide strong isolation and ensure uniform guest environments regardless of the underlying host platform. Virtual machines also allowed instructors to quickly reset or change a machine's state via snapshots without IT personnel present~\cite{stokerUsingVirtualMachines2013,harvieUsingVirtualMachines2019}. However, distributing multi-gigabyte virtual disk images imposes steep download times, slow boot sequences, and heavy hardware demands on student laptops~\cite{malanContainerizingCS50Standardizing2024,stokerUsingVirtualMachines2013}.

To reduce this virtualization overhead, educators shifted toward client-side and cloud-backed containerization to provide students with a complete development environment~\cite{valstarUsingDevContainersStandardize2020,malanContainerizingCS50Standardizing2024}. DevContainers leverage Docker to package compilers, runtimes, and editor extensions into a version-controlled container specification, ensuring that every enrolled student executes code in an identical software sandbox matching the course autograder~\cite{valstarUsingDevContainersStandardize2020}. Containers were also faster for staff to develop and for students to launch, starting in seconds rather than the minutes required to boot a full guest operating system~\cite{malanContainerizingCS50Standardizing2024,valstarUsingDevContainersStandardize2020}. However, this approach still incurs computational and storage overhead on client machines, requiring a background Linux virtual machine on Windows and macOS hosts and consuming significant disk space and working memory~\cite{valstarUsingDevContainersStandardize2020}.

\subsection{Learning Opportunity Provided from Managing Systems}

Despite the advantages that pre-configured containers provide, completely abstracting system configuration can also remove valuable hands-on exposure when system management itself is a pedagogical goal~\cite{harvieUsingVirtualMachines2019}. Harvie et~al.~\cite{harvieUsingVirtualMachines2019} note that deliberately requiring students to install server packages via Ubuntu's Advanced Packaging Tool (APT) and configure network ports inside a baseline virtual machine provided a practical learning opportunity that improved initial student comprehension of package management and client-server architectures. Conversely, in domain-focused courses and cybersecurity exercises where environment setup is merely a prerequisite rather than the learning objective, Gupta et~al.~\cite{guptaCTFArchiveCapture2025} demonstrate that requiring learners to manually reconstruct and rehost complex software environments creates a substantial entry barrier that diverts focus from conceptual mastery to technical troubleshooting.

\subsection{Declarative and Functional Package Management in Education}

To circumvent the heavy computational overhead of virtualized container engines while preserving reproducibility, educators and researchers have begun exploring purely functional package management via Nix Flakes~\cite{5BuildingReproducible,duNixRescueReproducible2026a}. Hasanovi{\'c}~\cite{5BuildingReproducible} reports on the migration of university C++ laboratory environments from Docker containers to declarative Nix Flake environments hosted on a public GitLab repository, allowing students to launch preconfigured Neovim, Visual Studio Code, and interactive C++ REPL development shells with a single command. Similarly, Du et~al.~\cite{duNixRescueReproducible2026a} demonstrate that Nix Flakes unify C/C++ and Python software stacks under a single declarative specification, providing full environment isolation and cross-project composition in user space without requiring root privileges.

The theoretical strengths of functional software deployment have been documented extensively in research literature~\cite{functionalSoftware,dolstraNixSafePolicyFree,dolstraPurelyFunctionalSystema,dolstraNixOSPurelyFunctional2010}. By treating package builds as pure functions whose outputs depend exclusively on cryptographically hashed inputs, Nix aims to guarantee that identical declarations yield identical store paths. Bandt~\cite{bandtAssessmentReproducibilityNix2025} conducts an empirical assessment of reproducibility in Nixpkgs, analyzing how functional package management mitigates non-deterministic build behaviors and how remaining sources of non-determinism can be detected. In scientific and academic computing, Hausch et~al.~\cite{hauschImprovingReproducibilityScientific2025} demonstrate through a case study on the preCICE multiphysics ecosystem that Nix/NixOS enables self-contained, reproducible research environments where traditional imperative Vagrant VM provisioning failed due to unpinned upstream dependencies. At the repository scale, Malka et~al.~\cite{malkaReproducibilityBuildEnvironments2024,malkaDoesFunctionalPackage2025} empirically validate build-environment reproducibility across space and time, successfully rebuilding 99.94\% of 14,000 packages from a six-year-old Nixpkgs revision and demonstrating bitwise reproducibility rates between 69\% and 91\% across 709,816 historical package builds.

Despite these reproducibility guarantees, adopting Nix introduces a significant usability trade-off. Du et~al.~\cite{duNixRescueReproducible2026a} emphasize that Nix imposes a relatively steep learning curve because its lazy functional language and packaging conventions are unfamiliar to most students and instructors alike. Hausch et~al.~\cite{hauschImprovingReproducibilityScientific2025} similarly observe that packaging complex software often requires workarounds for Nix's isolated \texttt{/nix/store} hierarchy that are difficult for non-experienced Nix users to implement, while Yin~\cite{OSCodeMy2024} highlights that sparse official documentation and cryptic evaluation error messages further elevate the entry barrier for newcomers. Notably, Du et~al.~\cite{duNixRescueReproducible2026a} observe in practice that LLM assistance can help lower this barrier by generating Nix expressions and diagnosing evaluation errors.

\subsection{Synthesis of Infrastructure as Code Using Large Language Models}

The rapid proliferation of Large Language Models has spurred widespread investigation into automating Infrastructure as Code (IaC) and system configuration management~\cite{kateGenerativeAIInfrastructure}. Rather than manually composing complex scripts, developers can specify deployment goals in natural language and delegate script generation to automated models. Srivatsa et~al.~\cite{srivatsaSurveyUsingLarge} conduct a comprehensive survey evaluating LLM capabilities across major declarative and procedural configuration platforms, noting that limited training data and rapidly evolving cloud APIs frequently cause models to produce syntactically plausible configurations that fail or introduce security risks in real-world deployments. This divergence stems from the models' lack of awareness of current best practices, platform updates, and complex multi-resource dependencies~\cite{srivatsaSurveyUsingLarge}.

Recent benchmark studies substantiate these findings. Kon et~al.~\cite{konIaCEvalCodeGeneration} introduce IaC-Eval, demonstrating that contemporary models like GPT-4 achieve only a 19.36\% pass@1 accuracy rate when generating declarative cloud infrastructure programs from natural language requirements, compared to 86.6\% on standard Python benchmarks. Similarly, Zhang et~al.~\cite{zhangDeployabilityCentricInfrastructureasCodeGeneration2025} emphasize that deployability, rather than surface syntax correctness, is the decisive metric for automated infrastructure generation, finding that state-of-the-art LLMs achieve only 20.8\% to 30.2\% first-attempt deployment success unless augmented with iterative verification and deployment feedback loops. A foundational vulnerability in automated code and environment synthesis is package hallucination~\cite{ImportingPhantomsMeasuring}. Krishna et~al.~\cite{ImportingPhantomsMeasuring} analyze package hallucination across Python, JavaScript, and Rust, demonstrating that LLMs frequently fabricate non-existent package identifiers—particularly in ecosystems with smaller registries and less training data representation such as Rust, where mean hallucination rates reach 24.74\% and exceed 42\% for several models. In software pipelines, these hallucinations break build executions and expose users to package squatting supply-chain attacks, underscoring the critical need for deterministic external package verification~\cite{ImportingPhantomsMeasuring}.

\subsection{Agentic Skills and Tool-Augmented Assistance}

While Nix Flakes offer strong reproducibility and lightweight execution, their lazy, purely functional configuration model~\cite{ModularityLazyEvaluation} poses a steep learning curve for students and faculty unfamiliar with functional package management~\cite{duNixRescueReproducible2026a,OSCodeMy2024}. Recent research in agent harness architectures demonstrates that the reliability of autonomous LLMs on complex, multi-step tasks is governed heavily by the surrounding harness—comprising the execution loop, tool registry, context management, and verification interfaces—rather than the base model alone~\cite{mengAgentHarnessLarge2026,formentScaffoldingMattersMore2026}. To structure domain-specific procedural knowledge within such harnesses, Agent Skills have emerged as modular, reusable packages that combine triggering metadata, workflow instructions, templates, and helper scripts~\cite{AgentSkills,lingAgentSkillsDataDriven2026}. Ling et~al.~\cite{lingAgentSkillsDataDriven2026} conduct a large-scale analysis of 40,285 public agent skills, showing that skills are heavily concentrated in software engineering and infrastructure workflows while remaining compact enough (with a median length of 1,414 tokens) to fit within standard prompt budgets without hard-coded orchestration rules. At the same time, security audits of public skill marketplaces reveal that unvetted third-party skills frequently introduce command-execution and data-exfiltration risks~\cite{beurer-kellnerTechnicalReportExploring2026,lingAgentSkillsDataDriven2026}, motivating carefully curated, sandboxed skill designs.

Integrating standardized tool protocols further strengthens agentic workflows. Inspired by the architectural decoupling of the Language Server Protocol (LSP) for development editors~\cite{borkLanguageServerProtocol2023}, the Model Context Protocol (MCP) defines a unified, bidirectional standard for connecting AI agents with external tools and data sources~\cite{MCPLandscape}. Although indiscriminate tool invocation can inflate token costs or degrade performance when unnecessary~\cite{wuCallNotCall2026,formentScaffoldingMattersMore2026}, coupling LLM reasoning with targeted, real-time package registry lookups and compiler verification provides a direct mechanism to ground package selection and mitigate the hallucination vulnerabilities identified in prior studies~\cite{ImportingPhantomsMeasuring,zhangDeployabilityCentricInfrastructureasCodeGeneration2025}.

\section{Nix Foundations}\label{sec:nix-foundations}

Having reviewed existing approaches and the emerging role of declarative tooling, this section establishes the fundamental Nix concepts required to understand its architectural advantages and operational limitations. Nix is both a package manager and a purely functional domain-specific language for describing how software dependencies and runtime environments are constructed. Unlike an imperative installation procedure, which modifies a shared system state step by step, a Nix expression describes the inputs from which a package or environment should be produced. Nix then evaluates that description and creates an immutable derivation. This distinction is central to the thesis: an agent generates a declarative specification rather than a sequence of host-specific installation commands.

\subsection{Declarative Packages and Nixpkgs}

In Nix, a \emph{derivation} is a build specification. It identifies the builder, its source inputs, build-time and run-time dependencies, configuration arguments, and expected outputs. Nix evaluates derivations as part of a dependency graph, allowing a package to depend on specific versions of compilers, libraries, and build tools rather than on whichever versions happen to be installed globally. The functional model aims to make a build result a function of its declared inputs, thereby avoiding hidden dependencies on mutable global directories~\cite{dolstraNixSafePolicyFree,dolstraPurelyFunctionalSystema}.

The collection of such package definitions is nixpkgs. It exposes packages as named attributes, such as \texttt{python3}, \texttt{cmake}, or \texttt{rustc}, and parameterizes many definitions by the target platform. A generated development environment therefore does not install packages by conventional system mutation; it selects attributes from a particular Nixpkgs revision and composes them into a shell or package output. This is why an invalid attribute name, a deprecated package, or a package unavailable on the target platform can prevent an otherwise plausible environment from evaluating. RQ1 evaluates whether the agent can make these selections correctly.

Declarative does not mean that every result is permanently identical in every context. Reproducibility depends on retaining the relevant input revisions, source artifacts, platform assumptions, and configuration. It also depends on the continued ability to obtain or build the required dependency closure. Consequently, the explicit declarations produced by Nix provide a strong basis for reproducibility, but they do not by themselves guarantee that a new student machine can activate an environment within an acceptable time.

\subsection{The Nix Store and Dependency Closures}

Nix places realized build outputs in the Nix store, conventionally \texttt{/nix/store}. Store paths are named with a cryptographic hash followed by a human-readable package name, for example \texttt{/nix/store/g33w0qxvkblmbqbpwnxdy1c8shji05gf-gcc-21.0.0}. The hash distinguishes the declared input configuration associated with that output. Store paths are treated as immutable once created, so an upgrade does not overwrite a library used by an existing environment; instead, it creates or selects a distinct store path. This permits multiple versions of a tool or library to coexist without sharing a mutable installation prefix~\cite{dolstraNixOSPurelyFunctional2010}.

Every realized package refers to other store paths that it requires at run time. The transitive set of those paths is its \emph{closure}. A development environment is therefore more than a short list of executables: it includes the compiler, libraries, interpreters, shell hooks, and other transitive dependencies needed by those executables. Nix makes this closure explicit and can construct a shell in which selected package binaries are available through \texttt{PATH}. The command \texttt{nix develop} is the primary interface used in this thesis to activate such a shell.

The store model explains both the benefit and the limitation evaluated by RQ2. A host on which an environment has already been used may contain a large, warmed store whose paths mask missing declarations or make activation appear faster than it would be for a student. The clean-container replay therefore starts each validation stage without a mounted host store or project directory. It tests whether the generated declaration and its transitive closure can be obtained and used independently of the authoring machine's prior state.

\subsection{Flakes, Locked Inputs, and Development Shells}

A flake is an experimental convention for organizing a Nix project around two files. The \texttt{flake.nix} file declares inputs and outputs. Inputs commonly include Nixpkgs, the nix package manager or other Git repositories; outputs may include packages, applications, NixOS configurations, or development shells. In this thesis, the relevant output is a \texttt{devShell}, which lists the tools and environment configuration required by a course assignment. A student activates that output with the \texttt{nix develop} nix command, which instantiates an ephemeral subshell containing all declared dependencies and environment variables from the generated \texttt{flake.nix} file.

The companion \texttt{flake.lock} file records resolved input revisions and associated metadata. It is a commitment to a specific dependency graph: once an instructor reviews and commits it, students use the same pinned inputs rather than silently receiving the newest revision of Nixpkgs. Updating an input with \texttt{nix flake update} is therefore a maintenance action that intentionally changes the lock file; it is not part of ordinary activation of a fixed course environment. Pinning supports repeatability across student machines, but a lock file is not an offline archive. If an input or store path is absent locally, Nix may still need network access to retrieve it.

\begin{lstlisting}[caption={\texttt{flake.lock} \texttt{nixpkgs} Attributes}, label={lst:flake-lock-nixpkgs-attributes}]
  "nixpkgs": {
    "locked": {
      "lastModified": 1791011291,
      "narHash": "sha256-V6OBJccNKBo/ktknxlJXZChPoI0NE2lembArBO3CE9k=",
      "owner": "NixOS",
      "repo": "nixpkgs",
      "rev": "73e728ddb6b7a12d18808f510813a13ee1fe4cce",
      "type": "github"
    },
  }
\end{lstlisting}

Here, the \texttt{rev} attribute designates the exact Git commit hash of the Nixpkgs repository pinned for the project, while \texttt{narHash} records the cryptographic hash of the serialized Nix Archive (NAR) content~\cite{ContentAddressingFileSystem}. By locking this commit and content hash, Nix ensures that all downstream student environments evaluate identical package expressions regardless of subsequent upstream updates.

This distinction is important for practical classroom deployment. An outage affecting a source host such as GitHub~\cite{GitHubActionsHit2026} can interfere with updating a flake and can also interfere with first use when a locked input has not yet been fetched. These cases should not be conflated with failure of an already available, locked environment. Likewise, an instructor's decision to refresh a lock file can reveal renamed, removed, or insufficiently maintained package attributes that were not present in the version used for a prior course offering.

\subsection{Realization, Binary Caches, and Trust}

Nix evaluation determines whether an expression is syntactically and semantically valid and identifies the derivations it requires. Realization obtains the corresponding store paths. During realization, Nix first attempts to substitute a pre-built store path from a configured binary cache; the public cache at \texttt{cache.nixos.org} is the set default~\cite{BinaryCacheOfficial,malkaDoesFunctionalPackage2025}. If no acceptable substitute is available, Nix can build the derivation from source, provided that its sources and build dependencies can be obtained. This fallback improves completeness but may require substantial time and local computing resources for large dependency closures.

A \emph{substituter} is an additional binary-cache endpoint~\cite{BinaryCacheOfficial}. It can reduce setup time by serving store paths that are absent from the primary cache, including course-specific builds maintained by an institution. However, cache use is also a supply-chain trust decision. Nix accepts binary substitutes according to configured public signing keys; adding a third-party cache together with its key expands the set of entities authorized to provide binaries that students execute. Thus, a substitute may improve availability while increasing the trusted computing base~\cite{dolstraNixSafePolicyFree,GarnixBlogStop}.

These mechanisms establish the technical basis for the operational constraints discussed in Section~\ref{sec:operational-constraints}. Classroom dependability relies on more than whether a \texttt{flake.nix} evaluates: locked inputs must remain obtainable when needed, package definitions must remain suitable for the course, required binaries must be available or buildable within the instructional time budget, and any cache used to improve availability must be explicitly trusted.

\section{Summary of Research Gaps}\label{sec:research-gaps}

Existing literature demonstrates a clear trade-off in managing development environments in computer science courses. Centralized servers introduce administrative friction and network vulnerabilities~\cite{valstarUsingDevContainersStandardize2020,malanContainerizingCS50Standardizing2024}. Virtual machines may introduce computational and storage loads that lower-end student machines struggle to handle~\cite{malanContainerizingCS50Standardizing2024,stokerUsingVirtualMachines2013}. DevContainers deliver standardized isolation at the expense of background virtualization on non-Linux hosts, disk storage consumption, and imperative image build layers~\cite{valstarUsingDevContainersStandardize2020,NixBetterDocker2024}. Nix Flakes offer a compelling alternative that balances native application performance, fine-grained reproducibility, and unprivileged execution~\cite{5BuildingReproducible,duNixRescueReproducible2026a}, yet their functional DSL and packaging conventions impose a steep learning curve that restricts broad classroom adoption~\cite{duNixRescueReproducible2026a,OSCodeMy2024,hauschImprovingReproducibilityScientific2025}.

Although modern LLMs excel at general-purpose code synthesis~\cite{chenEvaluatingLargeLanguage2021}, they exhibit low pass rates on declarative infrastructure specifications~\cite{konIaCEvalCodeGeneration,zhangDeployabilityCentricInfrastructureasCodeGeneration2025} and elevated package hallucination rates in less-represented ecosystems~\cite{ImportingPhantomsMeasuring}. No prior work has investigated combining specialized custom agent skills, real-time MCP registry retrieval, and deterministic Nix evaluation feedback to bridge the cognitive divide between natural language course requirements and functional development environments. This thesis directly investigates this unexplored intersection.
