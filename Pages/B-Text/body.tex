\chapter{Research Questions and Proposed Architecture}\label{RQ}

\section{Research Questions}\label{sec:rqs}

This thesis investigates the feasibility, reproducibility, and reliability of the ecosystem of automated declarative environment generation for computer science education. To guide empirical inquiry, three central Research Questions (RQs) are formulated:

\begin{enumerate}
	\item \textbf{RQ1 (Agentic Synthesis Accuracy):} Can an AI agent accurately infer system-level dependencies from natural language assignment instructions or unconfigured source code to automatically generate valid, reproducible \texttt{flake.nix} environments?
	\item \textbf{RQ2 (Clean OS Reproducibility):} To what extent do Nix Flake environments that pass local validation reproduce and support headless coursework tasks in a fresh Linux container and macOS VM without the authoring machine's files, configuration, or prior evaluation state?
	\item \textbf{RQ3 (Classroom Deployment Reliability and Student Ergonomics):} To what extent can Nix Flake environments provide a dependable foundation for classroom use, and what operational constraints and risk trade-offs shape that dependability? Is the use of Nix demonstrably better in terms of cognitive ergonomics
\end{enumerate}

\section{Proposed Solution: An agent skill for AI-Assisted Nix Flake Synthesis}\label{chap:solution}

To bridge the gap between complex declarative configurations and educational usability, we propose the use of an agent skill. Rather than forcing instructors or students to master the Nix DSL language, our agent skill delegates the composition, package resolution, and verification of Nix Flakes to an autonomous agent harness.

The end-to-end architecture comprises the following steps (illustrated at a high level in Figure~\ref{fig:pipeline-overview}):
\begin{enumerate}
	\item \textbf{Requirement Ingestion:} Specifications from natural language, existing codebases, or instructional documents on setting up compute environments are analyzed to extract inferred toolchains, language runtimes, and system-level libraries.
	\item \textbf{Specialized Agent Skill Scaffolding and Live Package Retrieval:} A custom agent skill provides domain-specific prompting, curated templates, and reference schemas. The skill also provides the agent the proper information to query a Model Context Protocol (MCP) server that reaches out to live NixOS search indices. In addition, deterministic Python helper scripts within the skill extract requirements from unstructured course documents and starter repositories to guide flake generation.
	\item \textbf{Deterministic Closed-Loop Verification:} Generated \texttt{flake.nix} files are evaluated via native Nix commands. If syntax or dependency errors occur, the compiler diagnostics are fed back into the agent harness for iterative self-correction.
	\item \textbf{Output Artifacts and Runtime Deployment:} A \texttt{flake.nix} file is written alongside a cryptographically pinned \texttt{flake.lock} file, immediately activating a reproducible developer shell.
\end{enumerate}

\section{Agentic Flake Synthesis Evaluation Protocol}\label{sec:rq1-methodology}

To investigate whether modern autonomous agents can reliably synthesize declarative Nix development environments from informal pedagogical requirements (RQ1), we established a rigorous benchmark evaluation protocol. This protocol couples structured curriculum task suites with an automated verification pipeline to measure synthesis accuracy, dependency resolution, and runtime execution determinism.

\subsection{Benchmark Dataset Curation and Curriculum Tracks}\label{subsec:dataset-curation}

Because standardized benchmark datasets for declarative Nix environments did not previously exist, we constructed an evaluation benchmark representing standard computer science coursework requirements. The evaluation suite consists of synthetic natural language assignment instructions that an instructor would provide to students, unconfigured starter codebases from which dependencies must be inferred, and instructional course documents formatted as PDF, DOCX, and Markdown files. The evaluation tasks are organized across two distinct curriculum tracks:
\begin{enumerate}
	\item \textbf{Software Development Track:} Curated assignments focusing on systems programming, compiler toolchains, and web engineering. These tasks require native compilers, build systems, and runtime interpreters, including C/C++ (GCC, Clang, CMake, GNU Make), Rust (Cargo, \texttt{rustc}), and full-stack environments (Python, Node.js).
	\item \textbf{Data Science Track:} Curated coursework requiring complex scientific computing stacks, numeric routines, and specialized packages, including Python (NumPy, SciPy, Pandas, PyTorch), R statistical environments, and Jupyter notebook kernels.
\end{enumerate}

The benchmark dataset is serialized as a \texttt{jsonl} file, where each record specifies the curriculum track, the natural language prompt or project path, and the set of required dependencies asserted for verification:

\begin{lstlisting}[caption={Input Data Format}, label={lst:input-data-format}]
  {
    "track": "...",
    "instruction": "...",
    "dependency": "...",
  }
\end{lstlisting}

In this format, \texttt{track} classifies the curriculum category, \texttt{instruction} represents the natural language prompt or specification provided to the agent, and the \texttt{dependency} field specifies the list of packages or executables that must be present in \texttt{PATH} when \texttt{nix develop} is invoked to evaluate agent performance.

\subsection{Agent Harness, Model Configurations, and Tooling Conditions}\label{subsec:agent-harness}

The experimental synthesis harness was implemented using the Antigravity CLI agent framework. This harness coordinates prompt delivery, tool routing, shell execution streaming, and error log capture in an isolated session.

To assess how model architecture and reasoning scale influence Nix expression synthesis, experiments were conducted across two frontier models: Google Gemini~3.8 Flash and GPT-OSS 120B, both configured with medium reasoning effort. Evaluating models across distinct parameter scales allows us to assess whether smaller, cost-effective models can synthesize functionally equivalent environments when equipped with appropriate contextual scaffolding.

To guide the agent and eliminate erratic zero-shot behavior, each agent session integrates our specialized \texttt{course-flake-generator} skill (introduced in Section~\ref{chap:solution}). The internal filetree structure of the custom agent skill follows standardized agentic skill packaging conventions:

\begin{lstlisting}[caption={Custom Skill Filetree Structure}, label={lst:custom-skill-filetree}]
.
├── README.md
├── SKILL.md
├── assets
│   ├── flake-devshell.template.nix
│   └── mcp-servers.template.json
├── references
│   ├── flake-patterns.md
│   ├── inferring-requirements.md
│   └── mcp-nixos.md
└── scripts
    ├── detect-project-requirements.py
    ├── extract-document-content.py
    └── validate-flake.py
\end{lstlisting}

The \texttt{assets/} directory bundles validated boilerplate templates for \texttt{devShells} across multi-architecture systems. The \texttt{references/} directory supplies documentation outlining common Nix idiomatic patterns and troubleshooting heuristics. The \texttt{scripts/} directory stores Python scripts to perform deterministic actions such as extracting text from user submitted documents. According to Ling et~al.~\cite{lingAgentSkillsDataDriven2026}, providing modular templates and clear reference bounds significantly improves behavioral consistency and task adherence in autonomous agents.

Additionally, we evaluated two distinct package discovery conditions:
\begin{enumerate}
	\item \textbf{Live Registry Retrieval via MCP-NixOS:} The agent queries the \texttt{mcp-nixos} FastMCP server, which communicates directly with the Elasticsearch index powering \texttt{search.nixos.org}. Because Nixpkgs hosts over 139,008 packages across 1,044 package sets, real-time index querying protects against package hallucinations, deprecated attribute paths, and naming drift~\cite{borkLanguageServerProtocol2023,ImportingPhantomsMeasuring}.
	\item \textbf{Native Nix CLI Discovery (Ablation Condition):} In this condition, the MCP server is withheld from the agent, forcing it to rely exclusively on parametric pre-training weights and native Nix command-line inspection tools (such as \texttt{nix search} and \texttt{nix-env -qaP}).
\end{enumerate}

An automated Python test runner was developed to execute test suites, capture agent tool call telemetry, stream shell outputs, and record execution success metrics. The runner logs detailed traces for every synthesis attempt to facilitate post-hoc telemetry analysis.

\subsection{Three-Stage Validation Pipeline and Pass@K Formulation}\label{subsec:pass-k-metric}

Synthesizing a declarative \texttt{flake.nix} file requires navigating a functional domain-specific language where surface syntactic correctness does not guarantee runtime deployability~\cite{zhangDeployabilityCentricInfrastructureasCodeGeneration2025}. To rigorously verify that generated environments are functional, every candidate flake must satisfy a three-stage automated validation pipeline:
\begin{enumerate}
	\item \textbf{Grammar and Evaluation Validity:} The command \texttt{nix flake check} evaluates the generated \texttt{flake.nix} with lock-file writes disabled, ensuring that the expression parses cleanly without syntax errors, missing attributes, or invalid type signatures.
	\item \textbf{Build and Realization Determinism:} The command \texttt{nix develop --command <test-cmd>} successfully enters the ephemeral shell and resolves all declared binaries on the \texttt{PATH}.
	\item \textbf{Functional Task Execution:} The assignment source code builds and passes its unit test suite inside the synthesized \texttt{devShell}, verifying that compiler toolchains and runtime headers interact correctly with project source files.
\end{enumerate}

To quantify synthesis reliability, we adapted the Pass@$k$ formulation from code generation literature~\cite{chenEvaluatingLargeLanguage2021}. Pass@$k$ measures the probability that at least one of $k$ generated candidate environments passes all validation stages, where we generate $n \ge k$ samples per task. For our evaluation, we set $k = 3$ and $n = 3$.

We use the unbiased estimator introduced by Chen et~al.~\cite{chenEvaluatingLargeLanguage2021}:
\[
	\mathrm{pass@}k := \underset{\text{Problems}}{\mathrm{E}} \left[ 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}} \right]
\]
where $n$ is the total number of generated candidate samples per task and $c$ is the number of samples that successfully pass all three validation stages.

\section{Clean-Environment Reproducibility Protocol}\label{sec:rq2-methodology}

RQ2 evaluates whether a successful local validation actually transfers to a fresh environment that has none of the authoring host's files, shell configuration, or prior evaluation state. The inputs contain only RQ1 trial artifacts that passed the three-stage local verifier and include both a generated \texttt{flake.nix} and its \texttt{flake.lock}. This design evaluates the reproducibility of the generated flake specification.

\subsection{Isolation Objectives and Threat Model}

On a local development machine, an existing warmed Nix store or globally installed host library may mask missing dependency declarations, creating a false impression of reproducibility. To isolate the environment from authoring host pollution, our protocol mandates that candidate flakes be tested in fresh, ephemeral guest environments where no host directories or store paths are mounted.

The harness streams a compressed copy of the trial into the guest environment and extracts it into guest-local temporary storage; no project directory or host Nix store is mounted. The guest instance is discarded when the stage finishes, so no writable state is shared across stages or trials. Network access remains available so that a first-use environment can retrieve its pinned inputs and binary-cache artifacts, and availability failures are recorded separately from configuration failures.

\subsection{Guest Replay Pipeline and Failure Taxonomy}

The guest-side verifier executes four sequential stages on each RQ1-passing artifact:
\begin{enumerate}
	\item \textbf{Locked Flake Evaluation:} \texttt{nix flake check} evaluates the generated flake with lock-file writes disabled.
	\item \textbf{Development-Shell Activation:} \texttt{nix develop --command true} verifies that the development shell can be activated.
	\item \textbf{Required Tool Availability:} Each executable listed in the original RQ1 dependency assertion is checked with \texttt{command -v} inside the development shell.
	\item \textbf{Headless Task Execution:} A curated per-task command set verifies applicable language runtimes, builds, dependency synchronization, or test commands. Graphical editor workflows, interactive credentials, and persistent database-service administration are excluded because they cannot be assessed consistently by a headless guest.
\end{enumerate}

The principal metric is the base OS reproduction rate: the proportion trials that complete every applicable container-side stage. Failures are classified as flake-evaluation failures, shell-activation failures, missing dependencies, functional task failures, or infrastructure failures (an executable doesn't exist for this specific architecture). For each trial, the harness records the source identifier, container image digest and system architecture, Nix version, command exit codes, standard output and error logs, and stage durations. These artifacts make it possible to distinguish a defective generated environment from a transient container or upstream package-source failure.

\section{Ecosystem Reliability and Student Ergonomics Protocol}\label{sec:rq3-methodology}

RQ3 evaluates the practical ergonomics and operational reliability of Nix Flakes from a student perspective. We tasked two undergraduate students and a graduate students with configuring a course development environment using both traditional manual instructions and an AI-generated \texttt{flake.nix} synthesized via our RQ1 pipeline.

\subsection{Controlled Availability and Upstream Maintenance Conditions}

A pinned \texttt{flake.lock} separates ordinary classroom activation from dependency maintenance: students should activate a committed lock file rather than invoke \texttt{nix flake update} during a lab. Consequently, failure to update an input hosted on GitHub is recorded separately from failure to activate an already locked environment. This distinction prevents a transient source-host outage from being mischaracterized as a failure of a fixed course environment.

The assessment considers four conditions. First, input-source availability records whether a locked input can be retrieved when absent locally and whether a deliberate update can resolve the course's declared upstream inputs. Second, package-maintenance review records deprecated, renamed, broken, or removed attributes encountered when an instructor refreshes a course lock file. Third, binary availability records whether each required store path is substituted from an approved cache or instead requires a local source build, together with elapsed setup time and completion within a classroom time budget. Finally, cache-trust review records the substituters and public signing keys accepted by the environment. Nix verifies cached paths against trusted keys; adding a third-party cache can improve availability, but it also expands the set of entities trusted to provide course binaries~\cite{dolstraNixSafePolicyFree}.

The experiment uses controlled availability conditions rather than waiting for public outages: normal operation; an unavailable input source during update; an unavailable primary cache; and an approved alternate cache. For each condition, the protocol records activation success, elapsed time, whether local compilation occurred, the failing endpoint or stage, and the configured cache keys. The principal outcome is the proportion of environments that become ready within the defined instructional time budget without accepting an unapproved cache key. This design treats availability and supply-chain trust as jointly necessary properties of a dependable classroom environment.

\subsection{Student Ergonomics and Onboarding Study}

To assess human ergonomics and onboarding friction, we conducted a controlled user study involving two undergraduate and two graduate computer science students. Each participant was tasked with configuring a course development environment using two contrasting methods: traditional imperative instructions from a course syllabus, and single-command activation via an AI-generated \texttt{flake.nix} file.

Each trial was executed in a fresh macOS Sonoma guest instance cloned from a clean snapshot. We recorded setup completion time, and the student's personal opinion on which setup was easier, and qualitative observations regarding environment comprehension.

\chapter{Empirical Results and Analysis}\label{chap:results}

\section{Flake Synthesis Accuracy and Model Comparison}\label{sec:model-results}

Our experimental evaluation revealed notable variations across model architectures, curriculum domains, and agent access to an MCP server. In our initial evaluations conducted without the custom agent skill, general-purpose LLMs exhibited a strong tendency toward imperative fallbacks. Specifically, when operating on a macOS test host, models frequently attempted to install missing packages imperatively via Homebrew (\texttt{brew install}), failing to produce a declarative \texttt{flake.nix} file entirely.

With the introduction of the \texttt{course-flake-generator} skill, the model behaved more consistently. The agent successfully adhered to the declarative flake pattern for over 85\% of standard software development prompts. However, curriculum domain complexity strongly influenced outcomes. While the Software Development track achieved high Pass@1 rates, prompts in the Data Science track exhibited higher initial failure rates. In data science workloads, complex library dependencies frequently prompted models to revert to imperative package managers unless explicitly constrained by skill validation scripts.

Under the Pass@3 metric, both models succeeded on at least one attempt for every assignment prompt in the benchmark, demonstrating that iterative sampling overcomes intermittent synthesis errors. However, the models differed noticeably in tool utilization. The weaker model, GPT-OSS 120B, made significantly fewer calls to the MCP server, relying more heavily on its parametric weights. This reduced tool utilization led to higher initial hallucination rates for less common package attributes, requiring multiple closed-loop feedback cycles to recover compared to Gemini~3.8 Flash.

\section{Tool Invocation and Telemetry Analysis}

The tool-call logs were analyzed to determine how the agent resolved package and command uncertainty while constructing a flake. This analysis complements the pass/fail synthesis metric: a successful flake does not reveal whether the agent relied on parametric knowledge, live package retrieval, or native command-line inspection to reach the result. MCP-server availability was controlled by the experimental harness; it was not a tool-selection decision made by the model.

\subsection{Native Nix CLI Discovery versus MCP Retrieval}

Our baseline experiments evaluated whether an agent strictly requires the \texttt{mcp-nixos} server for successful synthesis. In our testing script, we added a flag to run a condition in which the MCP server was not provided to the model. In that condition, the model still produced valid environments for the simple, conventional requirements represented in the dataset. The required toolchains, including standard language runtimes, compilers, and build tools, are widely documented nixpkgs attributes. The observed behavior is therefore consistent with the model recognizing common package conventions from prior exposure.

When the model encountered uncertainty in the no-MCP condition, it used native Nix CLI discovery. Test data shows invocations of commands such as \texttt{nix search}, \texttt{nix-env -qaP}, and help interfaces including \texttt{nix --help} or a subcommand's \texttt{--help} flag. These commands gave the agent sufficient information to inspect available attributes and refine its subsequent commands. In this benchmark, the Nix CLI therefore served as an effective, self-describing retrieval interface when the additional MCP layer was unavailable.

This result should not be interpreted as evidence that MCP retrieval is generally unnecessary. The telemetry records which tools the agent used when MCP access was withheld; it does not establish whether a result originated from training data, command output, or a combination of both. More specialized coursework, obscure package names, recently changed Nixpkgs attributes, or complex platform constraints may exceed what native CLI exploration can resolve efficiently. In those conditions, the structured and current metadata exposed by \texttt{mcp-nixos} remains a useful capability for reducing package hallucination and configuration drift~\cite{borkLanguageServerProtocol2023,ImportingPhantomsMeasuring}. The present result instead bounds the claim: for straightforward requirements, the model could construct a working flake without MCP access.

\section{Base OS Reproducibility Results}\label{sec:base-os-results}

The base OS replay evaluation measured the clean reproduction rate for eligible RQ1-passing artifacts across both isolated Linux containers and clean macOS Tart virtual machines, disaggregated by curriculum track and failure category. Across all replayed trials, artifacts that passed the host-side verification pipeline demonstrated a high container reproduction rate, confirming that declarative Nix Flakes effectively isolate dependencies from authoring host pollution.

Failures encountered during clean replay were categorized into evaluation errors, shell activation errors, missing runtime dependencies, and task execution failures. In the Software Development track, the primary failure mode stemmed from implicit assumptions regarding host-installed tools (such as native dynamic linkers or unpinned C standard library dependencies) that were present on the authoring host but absent in the minimal container image. The closed-loop verification pipeline captured these discrepancies, and once pinned in the flake specification, subsequent replays executed deterministically. In the Data Science track, replay failures predominantly occurred during Python package native extensions compilation when underlying C headers were not explicitly included in \texttt{buildInputs}. These outcomes demonstrate that host-side validation alone is insufficient; clean-environment replay is essential for certifying that an AI-synthesized development environment is truly hermetic.

\section{Ecosystem Reliability, Student Ergonomics, and Deployment Discussion}\label{sec:rq3-reliability-discussion}

RQ3 evaluates the dependability of Nix Flake environments under practical classroom constraints, identifying the operational conditions, human ergonomics, and supply-chain trust boundaries that shape long-term educational adoption.

\subsection{Student Ergonomics and Environment Onboarding}

To assess the human factors of adopting declarative environments, we conducted an onboarding trial with two undergraduate and two graduate computer science students. Each participant was tasked with configuring a development environment for a course project using both conventional imperative setup instructions and an AI-generated \texttt{flake.nix} environment.

Participants reported that traditional manual setup guides were error-prone, requiring substantial manual intervention to resolve version conflicts with pre-existing packages on their personal machines. In contrast, activating the declarative environment via \texttt{nix develop} required only a single terminal command once Nix was installed. The graduate students noted the distinct advantage of knowing their project dependencies would not collide with thesis or research software. However, participants also identified usability hurdles: the initial download time for store paths was non-negligible, and students unfamiliar with Nix found error messages confusing when attempting to install ad-hoc tools imperatively within the active shell. These results emphasize that while declarative flakes substantially lower onboarding friction, clear conceptual onboarding regarding Nix's read-only store model remains critical for classroom adoption.

\subsection{Operational Availability and Maintenance Conditions}

Classroom readiness within an instructional time budget depends heavily on normal operation, input source availability, primary cache availability, and approved binary cache conditions. Our analysis separates locked-environment activation from \texttt{nix flake update}, identifying package-maintenance failures encountered during lock refresh, and reporting source-build fallback and cache-key decisions without conflating an availability failure with an invalid flake.

Nix Flakes make dependencies explicit, but they do not eliminate dependence on the services and maintainers that supply those dependencies. Nixpkgs inputs are commonly fetched from GitHub. A GitHub outage can therefore prevent an instructor from refreshing a flake input and can prevent a new machine from fetching a locked input that is not already available locally. These are different operational events: a committed lock file protects ordinary coursework from unintended version drift, whereas updating the lock file remains an instructor maintenance activity that depends on upstream availability.

The breadth of Nixpkgs also creates a maintenance risk. Package definitions may become deprecated, renamed, broken, or removed when upstream software is abandoned or when no contributor continues to maintain its Nix expression. Pinning a course environment provides a stable term-level target, but it does not remove the need to review package availability before the next term or before updating a lock file. Instructors should therefore establish a refresh schedule, retain a tested lock file for the current offering, and identify a supported alternative when a course depends on a narrowly maintained package.

Finally, binary-cache misses turn an availability event into a student-facing time cost. A departmental cache or an approved external substituter can reduce that risk, but it must be governed as part of the course's trusted computing base. RQ3 consequently evaluates reliability as a combination of input availability, maintained package definitions, bounded setup time, and an explicit cache-trust policy rather than as a property of the \texttt{flake.nix} file alone.

\subsection{Security Considerations and Binary Cache Trust Boundaries}

Nix normally realizes a required store path by downloading a signed substitute from a binary cache; when no acceptable substitute is available, it may instead build the path locally from source. This fallback preserves the possibility of realization but can be unsuitable for a classroom when compilation exceeds the time available for a laboratory session. Thus, cache availability is an operational reliability concern rather than merely a performance optimization.

Nix can use additional binary caches, known as substituters, to improve availability. A substitute is accepted only when its signature corresponds to a configured trusted public key. This signature mechanism provides an integrity boundary, but adding an external cache and its key is a supply-chain decision: it authorizes that cache operator to provide binaries that students will execute. A course should therefore use only institutionally approved cache URLs and keys, document them in the course environment, and avoid asking students to trust arbitrary caches~\cite{dolstraNixSafePolicyFree}.
