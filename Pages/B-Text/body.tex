\chapter{Research Questions and Proposed Architecture}\label{RQ}

\section{Research Questions and Hypotheses}\label{sec:rqs}

This thesis investigates the feasibility, reproducibility, and reliability of automated declarative environment generation for computer science education. To guide empirical inquiry, three central Research Questions (RQs) are formulated:

\rqlist

To evaluate these questions systematically, we formulate four corresponding working hypotheses:
\begin{itemize}
	\item \textbf{H\textsubscript{1a}:} Providing structured procedural scaffolding (\texttt{course-flake-generator}) and closed-loop evaluation (\texttt{nix flake check}) will enable both frontier (\texttt{Gemini 3.8 Flash}) and smaller open-weight (\texttt{GPT-OSS 120B}) models to reliably synthesize valid \texttt{flake.nix} environments, narrowing the synthesis accuracy gap between model tiers.
	\item \textbf{H\textsubscript{1b}:} Augmenting the agent with real time data (\texttt{mcp-nixos}) will reduce package hallucinations and improve first-attempt synthesis accuracy (Pass@1) and package precision compared to relying on training data knowledge and native Nix CLI commands alone.
	\item \textbf{H\textsubscript{2}:} Nix Flake environments that pass the host validation pipeline with a pinned \texttt{flake.lock} will deterministically reproduce and support coursework execution in clean, unmounted Linux containers and macOS virtual machines, with any residual failures isolated to platform-specific package availability.
	\item \textbf{H\textsubscript{3}:} Single-command activation via \texttt{nix develop} will reduce procedural errors and cognitive friction compared to manual imperative installation.
\end{itemize}

\section{Proposed Solution: An agent skill for AI-Assisted Nix Flake Synthesis}\label{chap:solution}

To bridge the gap between complex declarative configurations and educational usability, we propose a custom agent skill that specializes an autonomous coding agent in synthesizing and verifying valid \texttt{flake.nix} specifications. Rather than requiring instructors or students to master the Nix expression language, the skill delegates dependency inference, package resolution, and build verification to the user's local agent harness. Although existing wrapper ecosystems such as \texttt{devenv} introduced an AI-assisted \texttt{devenv generate} command in version~1.4, that approach requires the installation of \texttt{devenv} tool and subsequently had its CLI codebase-inference capability removed following privacy concerns over telemetry that uploaded tracked repository files to external servers~\cite{goodingDevenvFacesBacklash2025}. In contrast, our proposed skill operates directly within the local agent harness to produce standard, zero-wrapper \texttt{flake.nix} configurations while inspecting project repositories and course documents locally.

Operating this synthesis pipeline requires a host environment that satisfies three baseline prerequisites. First, the host system must run a POSIX-compatible environment supported by the Nix package manager: Linux (natively or within Docker containers), macOS, or Microsoft Windows via the Windows Subsystem for Linux (WSL2). Second, Nix must be installed with experimental Flake support enabled. When using the official Nix installer, users must explicitly enable flakes by declaring \texttt{experimental-features = nix-command flakes} in either the user-level (\texttt{\textasciitilde/.config/nix/nix.conf}) or system-wide (\texttt{/etc/nix/nix.conf}) configuration file; alternatively, the Determinate Systems Nix installer enables these features by default without manual intervention. Third, a compatible agent harness must be installed to load the skill package and orchestrate tool execution. Because Agent Skills follow an open, modular specification consisting of structured Markdown instructions (\texttt{SKILL.md}), reference templates, and helper scripts~\cite{AgentSkills,lingAgentSkillsDataDriven2026}, our skill is portable across any agent harness that supports the standard skill directory convention and local shell tool invocation.

Operating through the instructor's local agent harness, the custom agent skill guides an assignment-to-flake workflow (illustrated at a high level in Figure~\ref{fig:pipeline-overview}) across six sequential stages:
\begin{enumerate}
	\item \textbf{Assignment document:} The instructor supplies existing coursework materials (such as an assignment handout in PDF, DOCX, HTML, or Markdown format, natural language instructions, or an unconfigured starter codebase) without needing to manually compose Nix expressions.
	\item \textbf{Requirement extraction:} The agent extracts required compilers, language runtimes, build tools, and system libraries from the provided materials. This capability is driven by the custom skill's bundled scripts: a document extraction script to parse unstructured assignment handouts, alongside a project detector that scans repository files and manifests for declared dependencies.
	\item \textbf{Flake generation:} Guided by the \texttt{course-flake-generator} skill's multi-architecture templates and reference heuristics, the agent synthesizes a declarative \texttt{flake.nix} specification. To resolve required package attributes deterministically, the skill primarily queries the \texttt{mcp-nixos} server against real-time Nixpkgs search indices, falling back to native Nix CLI inspection commands when the MCP server is not present.
	\item \textbf{Validation:} The candidate \texttt{flake.nix} is evaluated through closed-loop verification, executing \texttt{nix flake check} and ephemeral shell realization checks to detect syntax errors or missing executables. If failures occur, compiler diagnostics are returned to the agent harness for automated self-correction until validation passes and generates a pinned \texttt{flake.lock}.
	\item \textbf{Instructor approval:} The instructor reviews the synthesized \texttt{flake.nix} and cryptographically pinned \texttt{flake.lock} file and commits them to the assignment repository, establishing a verified, frozen dependency closure for the course.
	\item \textbf{Student activation:} Students clone the assignment repository onto their personal devices and run \texttt{nix develop} to enter the reproducible development shell, avoiding manual installation troubleshooting and working directly on the assignment.
\end{enumerate}

\section{Agentic Flake Synthesis Evaluation Protocol}\label{sec:rq1-methodology}

To investigate whether modern autonomous agents can reliably synthesize declarative Nix development environments from informal natural language requirements (RQ1), we established a benchmark evaluation protocol. This protocol couples structured curriculum task suites with an automated verification pipeline to measure synthesis accuracy, dependency resolution, and runtime execution determinism.

\subsection{Benchmark Dataset Curation and Evaluation Suites}\label{subsec:dataset-curation}

Because standardized benchmark datasets for declarative Nix environments did not previously exist, we constructed an evaluation benchmark representing standard computer science coursework requirements across three distinct instructional modalities:

\begin{enumerate}
	\item \textbf{Natural Language Specification Prompts:} Curated prompts representing informal assignments provided by instructors across two curriculum tracks:
	      \begin{itemize}
		      \item \emph{Software Development Track:} Assignments focusing on systems programming, compiler toolchains, and web engineering. These tasks require native compilers, build systems, and runtime interpreters, including C/C++ (GCC, Clang, CMake, GNU Make), Rust (Cargo, \texttt{rustc}), and full-stack environments (Python, Node.js).
		      \item \emph{Data Science Track:} Coursework requiring complex scientific computing stacks, numeric routines, and specialized packages, including Python (NumPy, SciPy, Pandas, PyTorch), R statistical environments, and Jupyter notebook kernels.
	      \end{itemize}
	      The prompt benchmark is serialized as a \texttt{jsonl} file, where each record specifies the curriculum track, the natural language prompt, and the asserted dependency list (Listing~\ref{lst:input-data-format}).

	\item \textbf{Existing Coursework Codebases:} A collection of project repositories collected from computer science coursework (\texttt{input/code\_bases/}) spanning artificial intelligence assignments, object-oriented Java laboratories, data structures projects, mobile app development, neural network coursework, and network programming. For these tasks, the agent cannot rely on explicit textual package lists; instead, the skill instructs the agent to run \texttt{detect-project-requirements.py} to inspect file contents, repository structures, and build manifests (such as \texttt{pom.xml}, \texttt{build.gradle}, and \texttt{pyproject.toml}) to infer necessary runtimes.

	\item \textbf{Instructional Course Documents:} A collection of course documents and laboratory setup guides (\texttt{input/docs/}) formatted as PDF, Microsoft Word (\texttt{.docx}), HTML, and Markdown files. To process these unstructured documents without manual keyword pre-mapping, the skill executes \texttt{extract-document-content.py} to parse layout structures into clean text for agent requirement extraction.
\end{enumerate}

To establish an objective evaluation standard across all three modalities, each task is paired with an evaluation schema defining ground-truth requirements. While synthetic prompt benchmarks are serialized as a unified \texttt{jsonl} file, each codebase directory and instructional document is paired with an individual companion metadata \texttt{.json} file (Listing~\ref{lst:input-data-format}). This metadata serves as the authoritative ground truth, manually verified by a human evaluator to establish the passing criteria for the assignment environment.

\begin{lstlisting}[caption={Evaluation Metadata Format and Ground-Truth Schema}, label={lst:input-data-format}]
{
  "title": "AI Assignments - Artificial Intelligence Course",
  "track": "computer science",
  "instruction": "Set up a Nix flake development environment...",
  "dependency_list": [
    "python3",
    "jupyter",
    "git"
  ]
}
\end{lstlisting}

In this schema, \texttt{track} classifies the curriculum domain, \texttt{title} and \texttt{instruction} provide contextual task descriptions, and \texttt{dependency\_list} designates the ground-truth executables that must resolve inside the ephemeral \texttt{nix develop} shell. The automated evaluation harness evaluates these human-verified assertions to determine whether candidate flakes satisfy the Pass@$k$ criteria and to compute package precision and over-provisioning metrics.

\subsection{Agent Harness, Model Configurations, and Tooling Conditions}\label{subsec:agent-harness}

The experimental synthesis harness was implemented using the Antigravity CLI harness. This harness coordinates prompt delivery, tool routing, and shell execution streaming.

We also wanted to assess how model architecture and reasoning scale influence Nix expression synthesis, experiments were conducted across two language models: Google Gemini~3.8 Flash and GPT-OSS 120B, both configured with medium reasoning effort. Evaluating models across different parameter scales allows us to assess whether smaller, cost-effective models can synthesize functionally equivalent environments when equipped with appropriate contextual scaffolding.

To guide the agent and eliminate erratic zero-shot behavior, each agent session integrates our specialized \texttt{course-flake-generator} skill (introduced in Section~\ref{chap:solution}). Additionally, we evaluated two distinct package discovery conditions:
\begin{enumerate}
	\item \textbf{Live Registry Retrieval via MCP-NixOS:} The agent queries the \texttt{mcp-nixos} FastMCP server, which communicates directly with the Elasticsearch index powering \texttt{search.nixos.org}. Because Nixpkgs hosts over 139,008 packages across 1,044 package sets, real-time index querying protects against package hallucinations, deprecated attribute paths, and naming drift~\cite{borkLanguageServerProtocol2023,ImportingPhantomsMeasuring}.
	\item \textbf{Native Nix CLI Discovery:} In this condition, the MCP server is withheld from the agent, forcing it to rely exclusively on parametric pre-training weights and native Nix command-line inspection tools (such as \texttt{nix search} and \texttt{nix-env -qaP}).
\end{enumerate}

An automated Python test runner was developed to execute test suites, capture agent tool call telemetry, stream shell outputs, and record execution success metrics. The runner logs detailed traces for every synthesis attempt to facilitate post-hoc telemetry analysis.

The artifacts generated within each benchmark run serve distinct functions for performance aggregation, behavioral auditing, and trial verification:

\begin{itemize}
	\item \texttt{benchmark\_summary.json}: Aggregates Pass@$k$ metrics, execution latency, token consumption, and dependency bloat scores across all trials. It serves as the primary machine-readable dataset for statistical analysis.
	\item \texttt{benchmark\_report.md}: Summarizes benchmark results, per-task score tables, and execution parameters in Markdown format. It provides an immediate overview of benchmark outcomes and links to individual agent sessions.
	\item \texttt{tool\_call\_frequency.csv}: Records the overall frequency, trial prevalence, and average invocations of every agent tool call. It quantifies how agent tool usage shifts between different model and grounding conditions.
	\item \texttt{tool\_call\_frequency\_by\_task.csv} and \texttt{tool\_call\_frequency\_by\_trial.csv}: Break down tool invocation distributions across specific tasks and individual trial samples. These matrices highlight task-specific variance and individual trial behavioral anomalies.
	\item \texttt{run\_command\_frequency.csv} and \texttt{run\_command\_base\_frequency.csv}: Tabulate exact and base shell commands executed through the agent harness. They reveal the CLI inspection patterns and build utilities invoked during synthesis.
	\item \texttt{run\_command\_log.csv}: Logs a complete, timestamped chronological trace of every shell command executed, its working directory, and associated metadata.
	\item \texttt{mcp\_tool\_frequency.csv} and \texttt{mcp\_tool\_log.csv}: Capture all registry search queries, filter arguments, and actions dispatched to the mcp server, if applicable.
	\item \texttt{agent\_response.md}: Preserves the final conversational completion message and instructions returned by the agent. It allows evaluators to verify the clarity and correctness of the agent's onboarding guidance.
	\item \texttt{flake.lock}: Pins exact cryptographic source hashes and input commits generated during local validation. It guarantees reproducible, deterministic evaluation across clean guest environments.
	\item \texttt{flake.nix}: Defines the declarative \texttt{devShell} environment and package inputs synthesized by the agent. It is the primary artifact tested against the three-stage validation pipeline.
	\item \texttt{jupyter\_install.html}: Contains the localized assignment specification or handout provided to the agent in document-grounded tasks. Isolating this input guarantees a self-contained trial workspace.
	\item \texttt{raw\_output.log}: Captures unbuffered standard output and standard error streams from the agent harness execution. It assists with post-mortem debugging whenever an execution hangs or crashes unexpectedly.
	\item \texttt{transcript.jsonl}: Stores the comprehensive turn-by-turn event stream, including internal reasoning traces, tool parameters, and raw tool responses. It provides full behavioral provenance for qualitative evaluation.
	\item \texttt{trial\_meta.json}: Records structured trial execution metrics, including pass/fail status, validation stages completed, latency, token usage, and dependency precision. It supplies the ground-truth values used to calculate Pass@$k$ and bloat statistics.
	\item \texttt{tool\_call\_frequency.csv}: Records the overall frequency, trial prevalence, and average invocations of every agent tool call. It quantifies how agent tool usage shifts between different model and grounding conditions.
	\item \texttt{tool\_call\_frequency\_by\_task.csv}: Cross-tabulates tool calls across individual coursework assignments. It reveals which problem domains provoked heavier tool utilization.
	\item \texttt{tool\_call\_frequency\_by\_trial.csv}: Maps tool invocations at the level of individual trial samples alongside validation success and duration. It facilitates fine-grained correlation between tool call patterns and task outcomes.
\end{itemize}

\subsection{Three-Stage Validation Pipeline and Pass@K Formulation}\label{subsec:pass-k-metric}

Synthesizing a declarative \texttt{flake.nix} file requires navigating a functional domain-specific language where surface syntactic correctness does not guarantee runtime deployability~\cite{zhangDeployabilityCentricInfrastructureasCodeGeneration2025}. To rigorously verify that generated environments are functional, every candidate flake must satisfy a three-stage automated validation pipeline:
\begin{enumerate}
	\item \textbf{Syntax and Evaluation Validity:} The command \texttt{nix flake check} evaluates the generated \texttt{flake.nix} with lock-file writes disabled, ensuring that the expression parses cleanly without syntax errors, missing attributes, or invalid type signatures.
	\item \textbf{Build and Realization Determinism:} The command \texttt{nix develop --command <test-cmd>} successfully enters the ephemeral shell and resolves all declared binaries on the \texttt{PATH}.
	\item \textbf{Functional Task Execution:} The assignment source code builds and passes its unit test suite inside the synthesized \texttt{devShell}, verifying that compiler toolchains and runtime headers interact correctly with project source files.
\end{enumerate}

To quantify synthesis reliability, we adapted the Pass@$k$ formulation from code generation literature~\cite{chenEvaluatingLargeLanguage2021}. Pass@$k$ measures the probability that at least one of $k$ generated candidate environments passes all validation stages, where we generate $n \ge k$ samples per task. For our evaluation, we set $k = 3$ and $n = 3$.

We use the unbiased estimator introduced by Chen et~al.~\cite{chenEvaluatingLargeLanguage2021}:
\[
	\mathrm{pass@}k := \underset{\text{Problems}}{\mathrm{E}} \left[ 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}} \right]
\]
where $n$ is the total number of generated candidate samples per task and $c$ is the number of samples that successfully pass all three validation stages.

\section{Clean-Environment Reproducibility Protocol}\label{sec:rq2-methodology}

RQ2 evaluates whether a successful local validation actually transfers to a fresh environment that has none of the authoring host's files, shell configuration, or prior evaluation state. The inputs contain only RQ1 trial artifacts that passed the three-stage local verifier and include both a generated \texttt{flake.nix} and its \texttt{flake.lock}. This design evaluates the reproducibility of the generated flake specification.

On a local development machine, an existing warmed Nix store or globally installed host library may mask missing dependency declarations, creating a false impression of reproducibility. To isolate the environment from authoring host pollution, our protocol mandates that candidate flakes be tested in fresh, ephemeral guest environments where no host directories or store paths are mounted.

The harness streams a compressed copy of the trial into the guest environment and extracts it into guest-local temporary storage; no project directory or host Nix store is mounted. The guest instance is discarded when the stage finishes, so no writable state is shared across stages or trials. Network access remains available so that a first-use environment can retrieve its pinned inputs and binary-cache artifacts, and availability failures are recorded separately from configuration failures.

\subsection{Guest Replay Pipeline and Failure Taxonomy}

The guest-side verifier executes four sequential stages on each RQ1-passing artifact:
\begin{enumerate}
	\item \textbf{Locked Flake Evaluation:} \texttt{nix flake check} evaluates the generated flake with lock-file writes disabled.
	\item \textbf{Development-Shell Activation:} \texttt{nix develop --command true} verifies that the development shell can be activated.
	\item \textbf{Required Tool Availability:} Each executable listed in the original RQ1 dependency assertion is checked with \texttt{command -v} inside the development shell.
	\item \textbf{Headless Task Execution:} A curated per-task command set verifies applicable language runtimes, builds, dependency synchronization, or test commands. Graphical editor workflows, interactive credentials, and persistent database-service administration are excluded because they cannot be assessed consistently by a headless guest.
\end{enumerate}

The principal metric is the base OS reproduction rate: the proportion trials that complete every applicable container-side stage. Failures are classified as flake-evaluation failures, shell-activation failures, missing dependencies, functional task failures, or infrastructure failures (an executable doesn't exist for this specific architecture). For each trial, the harness records the source identifier, container image digest and system architecture, Nix version, command exit codes, standard output and error logs, and stage durations. These artifacts make it possible to distinguish a defective generated environment from a transient container or upstream package-source failure.

\section{Student Onboarding Ergonomics Protocol}\label{sec:rq3-methodology}

RQ3 evaluates the practical ergonomics and setup time delta of Nix Flakes from a student perspective compared to traditional manual installation. To assess human ergonomics and onboarding friction, we conducted a controlled user study involving two undergraduate students and a graduate computer science student. Each participant was tasked with configuring a course development environment using two contrasting methods: traditional imperative instructions from a course document, and a \texttt{flake.nix} file that was generated from the above instruction guide using our custom agent skill.

Each trial was executed with 2 clones of a vanilla macOS virtual manager from Cirrus Labs, invoked via \texttt{tart run --dir=host:./ <student-A-dev>} where \texttt{--dir:} is the current directory of the AI generated flake. In the macOS VM, this becomes a shared volume, automatically providing the VM the required files.

We recorded total setup completion time, the time delta between imperative installation and declarative shell activation, the student's personal assessment of their preferred workflow, and qualitative observations regarding cognitive load.

We evaluated three progressively complex coursework environments to capture how setup time and procedural friction scale with dependency complexity. The first task required installing a single compiled language toolchain consisting of the Rust compiler and Cargo build system. The second task involved provisioning a data science environment with a Python runtime and the Jupyter Notebook package. Finally, the third task required configuring a multi-component full-stack web development environment integrating multiple language runtimes, package managers, and database utilities.

\chapter{Empirical Results and Analysis}\label{chap:results}

\section{Flake Synthesis Accuracy and Model Comparison}\label{sec:model-results}

Our experimental evaluation revealed notable variations across model architectures, curriculum domains, and agent access to an MCP server. In our initial evaluations conducted without the custom agent skill, general-purpose LLMs exhibited a strong tendency toward imperative fallbacks. Specifically, when operating on a macOS test host, models frequently attempted to install missing packages imperatively via Homebrew (\texttt{brew install}), failing to produce a declarative \texttt{flake.nix} file entirely, despite explicitly prompting the model.

With the introduction of the \texttt{course-flake-generator} skill, the model behaved more consistently. The agent successfully adhered to the declarative flake pattern for over 85\% of standard software development prompts. However, curriculum domain complexity strongly influenced outcomes. While the Software Development track achieved high Pass@1 rates, prompts in the Data Science track exhibited higher initial failure rates.

Under the Pass@3 metric, Gemini~3.8 Flash succeeded on at least one attempt for every assignment prompt in the benchmark (100.00\% Pass@3), whereas GPT-OSS~120B achieved 78.57\% Pass@3 with MCP access and 85.71\% without MCP access. These results partially support Hypothesis~\textbf{H\textsubscript{1a}}: structured procedural scaffolding and closed-loop validation enabled both the frontier model and the smaller open-weight model to synthesize functional environments across the majority of coursework prompts, though a performance gap persisted between model tiers. As detailed in Section~\ref{sec:telemetry-analysis}, this residual gap stemmed primarily from differences in tool utilization: GPT-OSS~120B made significantly fewer calls to the MCP server and relied more heavily and confidently on its training data without calling the nix cli search command, leading to higher initial hallucination rates for less common package attributes.

Table~\ref{tab:model-synthesis-results} summarizes the overall synthesis accuracy across both models with and without access to the \texttt{mcp-nixos} server, Table~\ref{tab:model-telemetry} reports mean trial duration and token consumption, and Table~\ref{tab:model-bloat} presents package precision and the over-provisioning (bloat) ratio across passing trials. To evaluate partial success, the evaluator extracts all package identifiers declared in \texttt{packages}, \texttt{buildInputs}, and \texttt{nativeBuildInputs} (exempting standard Nix formatters such as \texttt{nixfmt} or \texttt{alejandra}) and maps them against the expected CLI tools for each task. \emph{Package precision} measures the fraction of declared packages that directly satisfy an expected tool requirement (penalizing unrequested, extraneous packages), whereas the \emph{over-provisioning ratio} (bloat) computes the ratio of total declared packages to the minimum number of required packages needed to cover the expected tools, capturing both extraneous additions and redundant package declarations. Evaluating these metrics is critical because language models frequently introduce unrequested dependencies and extraneous configurations when generating declarative specifications~\cite{konIaCEvalCodeGeneration,zhangDeployabilityCentricInfrastructureasCodeGeneration2025,ImportingPhantomsMeasuring}.

A qualitative review of each trial's execution event stream (\texttt{transcript.jsonl}) and trial metadata revealed distinct failure modalities, behavioral patterns, and architectural differences between the two models:

\begin{enumerate}
	\item \textbf{Multi-Module Incompletion:} On coursework repositories with nested submodules, Gemini~3.8 Flash systematically iterated across every directory or authored module-specific flakes as required. In contrast, GPT-OSS~120B suffered from premature task termination. In \texttt{COSC236\_Labs} (Trial~2), the model authored flakes for \texttt{Lab1} and \texttt{Lab2}, emitted a conversational status message listing ``Next steps'', and concluded execution after only 26.8\,s, omitting Labs~3 through~10. Similarly, in Trial~3 of the same task, it generated flakes for Labs~1 through~9 but skipped \texttt{Lab10}. In \texttt{COSC336-Assignments} (Trial~1), it authored flakes for Assignments~1 through~6 but failed to process Assignments~7 and~8.
	\item \textbf{Package Hallucination:} When analyzing Python projects without explicit requirements manifests (\texttt{AI-Assignments}, Trial~3), GPT-OSS~120B fell back to treating language-level libraries as top-level Nixpkgs derivations, declaring \texttt{pkgs.pandas} and \texttt{pkgs.matplotlib} in \texttt{packages} rather than constructing an idiomatic \texttt{python3.withPackages} environment. This triggered immediate Nix evaluation failure: \textit{"error: attribute 'pandas' in selection path 'pkgs.pandas' not found. Did you mean pandoc?"}. In contrast, Gemini~3.8 Flash leveraged the skill's reference guides to properly structure Python environments using \texttt{python3.withPackages (ps: with ps; [ pandas matplotlib ])}.
	\item \textbf{Indiscriminate Over-Provisioning and Activation Timeouts:} In \texttt{COSC336-Assignments} (Trial~2), GPT-OSS~120B observed LaTeX assignment documentation alongside Java source files and added \texttt{pkgs.texliveFull} to \texttt{nativeBuildInputs}. Because \texttt{texliveFull} is about a 7gb package, downloading and substituting store paths exceeded the test harness's 60-second activation threshold, triggering an activation timeout failure.
	\item \textbf{Empty Output Errors:} In several document-grounded trials (such as Task~4 Trial~3 and Task~8 Trial~1), GPT-OSS~120B generated empty conversational responses between background tool calls, triggering harness runtime errors (\textit{"model output error: model output must contain either output text or tool calls"}) and exiting prior to generating \texttt{flake.nix}.
	\item \textbf{Naming Drift on Deprecated Packages:} On the database setup guide (\texttt{Itec 451 Mcguire1}), all three GPT-OSS~120B trials failed because the model repeatedly declared \texttt{pkgs.mysql}, which has been removed and replaced by \texttt{mariadb} and versioned attributes (\texttt{mysql80}) in Nixpkgs~24.11. Because the model withheld MCP search calls and relied exclusively on parametric weights, it was unable to detect and recover from attribute renaming.
	\item \textbf{Nix Identifier Syntax Violations:} In the full-stack Elixir task (\texttt{Fullstack Elixir Sqlite Evaluation}, Trial~2), GPT-OSS~120B attempted to declare Node.js via \texttt{nodejs-20\_x}. In Nix syntax, unquoted hyphens in attribute identifiers are evaluated as subtraction operators, causing Nix to fail with \textit{"error: undefined variable 'nodejs-20\_x'"}.
\end{enumerate}

Interestingly, on passing trials, GPT-OSS~120B achieved a higher package precision (87.1\% vs. 42.2\%) and a lower over-provisioning ratio (1.80$\times$ vs. 3.73$\times$) than Gemini~3.8 Flash on existing codebases. Transcript inspection explains this apparent paradox: when GPT-OSS~120B succeeded, it generated strictly minimalist flakes containing only the core compilers explicitly tested by the verifier (such as \texttt{openjdk17} or \texttt{pythonEnv}). Conversely, Gemini~3.8 Flash proactively inferred and provisioned comprehensive developer tooling suites detected within project files, including version control (\texttt{git}), build automation tools (\texttt{gradle}, \texttt{just}), and data science libraries (\texttt{torch}, \texttt{torchvision}, \texttt{scikit-learn}, and Jupyter kernels). While these auxiliary packages were penalized as extraneous under the strict CLI assertion baseline, they reflect a more complete, production-ready developer environment for students.

This tension between minimal specification adherence and unprompted over-generation is well documented in automated infrastructure synthesis. In their benchmark evaluation on Infrastructure as Code, Kon et~al.~\cite{konIaCEvalCodeGeneration} demonstrated that over 50\% of configurations that successfully passed compiler checks violated user intent specifications by provisioning unrequested, extraneous cloud resources and services. Similarly, Zhang et~al.~\cite{zhangDeployabilityCentricInfrastructureasCodeGeneration2025} observed that fewer than 26\% of synthesized deployment templates adhered to user-intended resource and attribute boundaries without inserting self-defined properties or unneeded substitutions. In our educational setting, however, qualitative analysis reveals an important distinction: whereas prior benchmarks observed unprompted resources arising from model hallucination or prompt divergence, Gemini~3.8 Flash's over-provisioning stemmed from proactive contextual inference. By scanning repository manifests for unstated but practical workflow requirements, the agent prioritized classroom deployability over minimal ground-truth precision.

Finally, the execution telemetry reported in Tables~\ref{tab:codebase-results} and~\ref{tab:doc-results} reveals a substantial divergence in execution characteristics. GPT-OSS~120B operated significantly faster than Gemini~3.8 Flash (averaging 77.31\,s vs. 324.58\,s on codebases, and 48.79\,s vs. 232.38\,s on documents) and consumed nearly an order of magnitude fewer tokens (38,459 vs. 261,714 on codebases, and 30,873 vs. 202,707 on documents).

\section{Tool Invocation and Telemetry Analysis}\label{sec:telemetry-analysis}

The tool-call logs were analyzed to determine how the agent resolved package and command uncertainty while constructing a flake. This analysis complements the pass/fail synthesis metric: a successful flake does not reveal whether the agent relied on parametric knowledge, live package retrieval, or native command-line inspection to reach the result. MCP-server availability was controlled by the experimental harness; it was not a tool-selection decision made by the model.

\subsection{Native Nix CLI Discovery versus MCP Retrieval}

Our baseline experiments evaluated whether an agent strictly requires the \texttt{mcp-nixos} server for successful synthesis. In our testing script, we added a flag to run a condition in which the MCP server was withheld from the model. Even without MCP access, the model produced valid environments across the benchmark by combining native Nix CLI discovery with its parametric knowledge of the Nixpkgs derivation schema. Guided by the skill's procedural directive to verify that every resolved package attribute evaluates cleanly prior to finalizing \texttt{flake.nix}, the agent followed a progressive resolution workflow across the trial transcripts.

First, when resolving a target requirement from the prompt, the agent invoked \texttt{nix search} (e.g., \texttt{nix search github:NixOS/nixpkgs/nixos-24.11 dotnet-sdk}) or \texttt{nix-env -qaP} to identify candidate attribute names. Listing~\ref{lst:nix-search-output} illustrates representative output returned by \texttt{nix search} during package discovery. In addition to attribute paths and version numbers, the command supplies concise package descriptions that assisted the agent in disambiguating similar tools and identifying the appropriate derivation.

\begin{lstlisting}[caption={Example \texttt{nix search} Output for Package Discovery}, label={lst:nix-search-output}]

Second, because Nixpkgs frequently exposes both unversioned default aliases and version-pinned attributes (such as \texttt{dotnet-sdk} alongside \texttt{dotnet-sdk\_8} and \texttt{dotnet-sdk\_9}), the agent executed targeted \texttt{nix eval} expressions to disambiguate candidates before writing the flake. Specifically, even though the skill documentation did not supply a cheat sheet of derivation attributes, the model leveraged its pre-trained knowledge of Nix idioms to query \texttt{.name} and \texttt{.version} (e.g., \texttt{nix eval github:NixOS/nixpkgs/nixos-24.11\#dotnet-sdk.name} and \texttt{nix eval --expr 'with import <nixpkgs> \{\}; openjdk17.name'}) to confirm concrete upstream versions; \texttt{.passthru.home} and \texttt{.outPath} to resolve store paths for environment variables such as \texttt{JAVA\_HOME} and \texttt{DOTNET\_ROOT}; \texttt{builtins.attrNames} (e.g., \texttt{builtins.attrNames pkgs.vscode-extensions}) to enumerate nested extension sets and test \texttt{vscode-with-extensions.override} expressions; and \texttt{.meta.platforms}, \texttt{.meta.broken}, and \texttt{.meta.license} to diagnose macOS (\texttt{aarch64-darwin}) compatibility for packages such as \texttt{rstudio} and \texttt{mysql-workbench}. In this benchmark, the Nix CLI therefore served as an effective, self-describing retrieval and verification interface when the MCP layer was unavailable.

Our findings align with observations by Forment et~al.~\cite{formentScaffoldingMattersMore2026}, indicating that the impact of external tool scaffolding on token efficiency depends heavily on harness implementation and task complexity. In our telemetry, access to the \texttt{mcp-nixos} server revealed a clear trade-off: external tool grounding incurred a minor token overhead on simple tasks, yet prevented runaway troubleshooting loops and token inflation on complex environments.

For tasks involving standard packages with unambiguous derivation names (such as \texttt{python312}, \texttt{uv}, \texttt{go}, or \texttt{openjdk}), providing MCP server access resulted in higher overall token consumption. This overhead stemmed from two primary factors. First, supplying the MCP tool schema injected an additional 400 to 450 prompt tokens into the context window on every agent step. Second, the agent frequently initiated proactive exploratory queries (executing 2 to 4 MCP search queries for unambiguous tools like \texttt{python312} and \texttt{uv}) prior to drafting \texttt{flake.nix}. In contrast, when MCP access was withheld, the agent relied directly on its training data to synthesize the flake in fewer turns without exploratory retrieval overhead.

Conversely, for complex tasks requiring wrapper derivations, ambiguous attributes, or platform-specific builds (such as \texttt{gcc}, \texttt{cmake}, \texttt{rustup}, \texttt{R}, and \texttt{rstudio} on macOS), token consumption exploded in the absence of an MCP server. In Task~10 (\texttt{R}), the agent without MCP access executed numerous \texttt{nix shell}, \texttt{nix search}, and \texttt{grep} commands to determine whether \texttt{R} was an isolated derivation or required specialized wrapper scripts, increasing mean token consumption from 204,402 to 250,211 tokens (+22.4\%). This divergence escalated dramatically in Task~11 (\texttt{RStudio}): in Trial~1 of the unassisted condition, the agent spiraled into an extensive troubleshooting loop lasting 133 steps, 92 shell commands, and 508,739 tokens. Without structured schema retrieval, the model attempted exhaustive \texttt{nix search} queries, evaluated raw Nix store derivations, inspected \texttt{/nix/store/.../wrapper-rstudio.nix} via \texttt{cat}, and even reverted to imperative Homebrew invocations (\texttt{brew install --cask rstudio}) while parsing macOS application bundle crash logs before finally realizing a functional flake. Under such conditions, the live metadata exposed by \texttt{mcp-nixos} acts as an indispensable constraint boundary that halts combinatorial shell exploration.

This result should not be interpreted as evidence that MCP retrieval is generally unnecessary. The telemetry records which tools the agent used when MCP access was withheld; it does not establish whether a successful derivation originated from parametric memory, shell command output, or an interactive combination of both. The \texttt{mcp-nixos} server is particularly advantageous for rapidly evolving packages or tracking unstable channels where parametric knowledge has decayed. Under those conditions, the structured, live metadata exposed by \texttt{mcp-nixos} remains an essential mechanism for mitigating package hallucination and configuration drift~\cite{borkLanguageServerProtocol2023,ImportingPhantomsMeasuring}. The present benchmark instead bounds the claim: for established core toolchains, an agent equipped with procedural scaffolding can construct a working flake using native CLI facilities alone.

When the \texttt{mcp-nixos} server was provided, the two models exhibited a stark divergence in tool adoption, as summarized in Table~\ref{tab:mcp-invocation-comparison} and illustrated across individual trials in Figure~\ref{fig:mcp-calls-by-trial}. Gemini~3.8 Flash invoked \texttt{call\_mcp\_tool} 136 times across all 40 completed trials (100.00\% trial prevalence, averaging 3.40 MCP calls per trial and accounting for 8.41\% of its 1,617 total tool invocations). Furthermore, Gemini~3.8 Flash leveraged the full breadth of the \texttt{mcp-nixos} schema, combining package and program \texttt{search} queries, detailed \texttt{info} lookups, \texttt{channels} verification, and binary \texttt{cache} checks on \texttt{aarch64-darwin}. In contrast, GPT-OSS~120B invoked \texttt{call\_mcp\_tool} only 6 times across just 3 of 41 completed trials (7.32\% trial prevalence, averaging 0.15 MCP calls per trial, or 1.02\% of its 590 total tool calls), restricting its queries to basic package searches without ever invoking \texttt{info} or \texttt{cache} actions.

Detailed inspection of the trial transcripts explains why GPT-OSS~120B systematically bypassed the MCP server. In 24 of its 41 trials (58.54\%), the model began execution by calling \texttt{list\_resources}. Because the \texttt{mcp-nixos} server exposes dynamic callable tools (\texttt{search} and \texttt{info}) rather than static file-like resources, \texttt{list\_resources} returned an empty JSON list. Misinterpreting this empty response as an indication that the server provided no operational capabilities, GPT-OSS~120B aborted further MCP interactions and defaulted entirely to its parametric weights and native shell commands.

The fact that models can fallback to native Nix CLI commands raises an essential question: why did GPT-OSS~120B still experience high failure rates on data science tasks despite having access to the exact same shell environment as Gemini~3.8 Flash? Telemetry and log analysis reveal that fallback to the Nix CLI is only effective when coupled with active, closed-loop diagnostic exploration. While Gemini~3.8 Flash engaged in multi-turn closed-loop verification (averaging 324.58\,s per trial and executing anticipatory \texttt{nix eval} queries to inspect derivation attributes and platform compatibility), GPT-OSS~120B operated in a single-turn mode (averaging 1.0 agent turn and 77.31\,s per trial). Rather than using the CLI for exploratory discovery, GPT-OSS~120B treated \texttt{nix develop} merely as a passive check at the end of its turn.

Furthermore, GPT-OSS~120B exhibited strong overconfidence in its parametric weights, which predated breaking changes introduced in Nixpkgs~24.11. Because the model assumed it already knew the correct package names, it did not invoke \texttt{nix search} before authoring the flake. Consequently, it directly emitted deprecated or improperly cased attribute names, such as specifying the removed top-level \texttt{mysql} attribute instead of \texttt{mysql80}/\texttt{mysql84} or lowercase \texttt{r} instead of \texttt{R}. When Nix evaluation failed, printing explicit compiler hints to the terminal (e.g., \textit{"Did you mean one of R, h, hr, ir or j?"} or \textit{"error: 'mysql' has been renamed to/replaced by 'mariadb'"}), GPT-OSS~120B failed to parse the diagnostic output or launch follow-up discovery commands to remediate the attribute name. In addition, when confronted with unfree licensing and platform restrictions on macOS (such as Android SDK licenses for Flutter or Darwin compatibility for \texttt{rstudio} and \texttt{mysql-workbench}), GPT-OSS~120B lacked the introspection scaffolding to set \texttt{config.allowUnfree = true} or evaluate \texttt{.meta.platforms}, triggering fatal activation aborts.

Taken together, the synthesis accuracy and telemetry findings offer a nuanced verdict on Hypothesis~\textbf{H\textsubscript{1b}}. While access to \texttt{mcp-nixos} consistently improved package precision (from 91.2\% to 93.3\% for Gemini~3.8 Flash and from 92.8\% to 93.5\% for GPT-OSS~120B) and reduced package over-provisioning (Table~\ref{tab:model-bloat}), live MCP retrieval was not strictly required to maximize first-attempt Pass@1 accuracy on well-established coursework packages because a capable model could substitute native Nix CLI introspection (\texttt{nix search} and \texttt{nix eval}). However, external registry grounding remains indispensable for open-weight models that exhibit rigid parametric priors and lack proactive closed-loop error recovery.

\section{Base OS Reproducibility Results}\label{sec:base-os-results}

The base operating system replay evaluation investigated the cross-platform reproducibility of eligible artifacts that passed host-side validation during the RQ1 synthesis benchmark. Each passing \texttt{flake.nix} and corresponding lockfile was evaluated across two isolated, clean environments: disposable Linux Docker containers running on an unprivileged host architecture and clean macOS virtual machines managed via the Tart virtualization framework. Replay trials executed an automated five-stage verification pipeline matching the host harness: static flake syntax check (\texttt{flake\_check}), development shell realization and hook execution (\texttt{activation}), binary presence verification on \texttt{PATH} for every declared dependency (\texttt{missing\_dependency}), and headless task command verification (\texttt{task\_<index>}). Replay outcomes were systematically classified according to the taxonomy implemented in \texttt{replay\_clean\_docker.py}, separating packaging errors from runtime functional execution errors.

Figure~\ref{fig:rq2-linux-results} and Figure~\ref{fig:rq2-macos-results} present the clean replay outcomes across the Computer Science and Data Science curriculum tracks for Linux and macOS, respectively. Across both operating systems, the generated flakes demonstrated robust structural isolation: zero trials encountered \texttt{flake\_failure}, \texttt{activation\_failure}, or \texttt{missing\_dependency}. In every instance, the Nix evaluator built the requested development shell derivation, populated the store paths, executed shell hooks without fatal exit codes, and placed all required tool binaries on the active \texttt{PATH}. Nevertheless, a subset of trials experienced \texttt{functional\_failure}, wherein the environment successfully activated with all dependencies present, but task-specific headless test commands exited with non-zero status codes.

In the Linux container replay (Figure~\ref{fig:rq2-linux-results}), 34 of the 41 eligible trials reproduced successfully without manual intervention, achieving an overall clean reproduction rate of 82.9\%. Across curriculum tracks, the Computer Science track achieved an 83.3\% reproduction rate (25 reproduced, 5 functional failures out of 30 trials), while the Data Science track achieved an 81.8\% reproduction rate (9 reproduced, 2 functional failures out of 11 trials). In the clean macOS virtual machine replay (Figure~\ref{fig:rq2-macos-results}), 39 of the 41 eligible trials reproduced successfully, yielding a 95.1\% overall clean reproduction rate. Specifically, the Computer Science track attained 93.3\% reproducibility (28 reproduced, 2 functional failures out of 30 trials), while the Data Science track achieved 100.0\% reproducibility (11 reproduced, 0 functional failures out of 11 trials).

Detailed post-mortem analysis of the trial logs revealed that all seven Linux failures and both macOS failures stemmed from three distinct root causes within the \texttt{functional\_failure} classification:

\begin{enumerate}
	\item \textbf{Container Privilege Boundaries and Electron Headless Sandboxing:} In the Linux Docker replay environment, all trials for the code editor environment failed during the headless verification of Visual Studio Code (\texttt{code --version}). The containerized replay harness executed inside disposable, headless Docker containers operating under the superuser (\texttt{root}) account. Visual Studio Code, built on the Electron framework, enforces a strict sandboxing policy that rejects execution under root privileges in headless Linux environments without explicit runtime flags, terminating immediately with the diagnostic: \textit{"You are trying to start Visual Studio Code as a super user which isn't recommended. If this was intended, please add the argument --no-sandbox and specify an alternate user data directory using the --user-data-dir argument."} In contrast, local host verification executed under a standard unprivileged user account, allowing \texttt{code --version} to exit cleanly. Similarly, on the clean macOS Tart virtual machines, the evaluation runner operated under the unprivileged \texttt{admin} user, where Darwin application bundles do not enforce Linux-specific container sandbox restrictions; as a result, all corresponding trials reproduced cleanly on macOS.
	\item \textbf{Host State Pollution via Mutable Toolchain Shims:} Across both Linux and macOS, multiple trials failed during the compiler verification command (\texttt{rustc --version \&\& cargo --version}) for the Rust toolchain environment. When synthesizing the development environment from prompt instructions requiring \texttt{rustup}, the agent declared the Nixpkgs derivation \texttt{pkgs.rustup} in \texttt{buildInputs} rather than the standalone compiler derivations \texttt{pkgs.rustc} and \texttt{pkgs.cargo}. In Nixpkgs, the \texttt{rustup} package provides proxy shims for \texttt{rustc} and \texttt{cargo} that dynamically resolve to toolchains managed under the user's mutable home directory (\texttt{\$HOME/.rustup}). On the author's local workstation, a default stable toolchain was already cached in \texttt{\textasciitilde/.rustup}, masking the uninitialized state and permitting the shims to execute during local RQ1 validation. When deployed to pristine guest environments where \texttt{\$HOME/.rustup} was empty, calling \texttt{rustc} failed with the diagnostic: \textit{"error: rustup could not choose a version of rustc to run, because one wasn't specified explicitly, and no default is configured."} In contrast, one synthesized trial succeeded on both Linux and macOS because the model included \texttt{rustup default stable} inside the flake's \texttt{shellHook}, dynamically bootstrapping the toolchain into the clean environment prior to command verification.
	\item \textbf{Absence of Display Server for Graphical Applications:} In the Data Science track, trials for the database administration environment failed during the verification command (\texttt{mysql-workbench --version}) during Linux container replay. MySQL Workbench is a desktop client application compiled against GTK and X11 graphical libraries. When invoked inside the minimal headless Docker container, the binary attempted to initialize a connection to a non-existent graphical display server, terminating with the runtime fault: \textit{"(mysql-workbench-bin): Gtk-WARNING **: cannot open display:"}. On the authoring host workstation, an active display server session was accessible. In the macOS virtual machine environment, Darwin application binaries and command wrappers do not depend on an X11 display socket, allowing all corresponding trials to execute without failure.
\end{enumerate}

These findings provide strong empirical validation for Hypothesis~\textbf{H\textsubscript{2}}, demonstrating that declarative Nix Flakes deliver high cross-platform determinism (95.1\% on macOS and 82.9\% on Linux) with zero environment-realization or missing-dependency failures. Crucially, the diagnostic failure taxonomy reveals an important distinction between \textit{infrastructure-induced evaluation artifacts} and \textit{authentic specification defects}. Five of the seven observed failures on Linux, specifically those involving graphical applications, were artifacts of the headless container test harness running under superuser privileges and lacking an X11 display server. Because student devices operate in unprivileged user accounts with graphical capabilities, these container-specific execution constraints do not impact practical student onboarding. Conversely, the failures observed during the Rust toolchain replay represent genuine specification defects resulting from host-state leakage, wherein mutable toolchain shims silently relied on ambient host caches. This underscores that clean-room replay in pristine guest environments is indispensable for validating that generated development flakes achieve true hermetic isolation.

\subsubsection{Student A}
During the imperative installation trial, Student~A completed the setup in 3~minutes and 21.22~seconds, but encountered multiple points of procedural friction along the way. Most notably, Student~A initially assumed that the leading shell prompt symbol (\texttt{\$}) printed in the documentation was a literal part of the command string to be executed. Furthermore, Student~A overlooked a critical post-installation instruction requiring them to source the Cargo environment script (\texttt{source "\$HOME/.cargo/env"}), which caused subsequent verification commands (\texttt{rustc --version} and \texttt{cargo --version}) to fail with command-not-found errors and created confusion regarding whether the compiler had actually been installed. This observation highlights a fundamental vulnerability of imperative installation guides: because manual procedures consist of stateful, sequential steps, inadvertently skipping a single environment-configuration step silently breaks downstream verification even when the underlying binaries have been downloaded successfully.

In the declarative Nix Flake trial, Student~A completed the setup in 4~minutes and 54.86~seconds, representing an additional 1~minute and 33.64~seconds compared to the imperative workflow. The majority of the time was spent waiting for the one-time installation of Nix itself and the initial realization of the development shell via \texttt{nix develop}. Despite the longer total wait time, Student~A expressed a clear preference for the declarative Nix Flake method, noting that once Nix was installed, activating the environment required a single deterministic command.

\subsubsection{Student B}
During the imperative installation trial, Student~B required 5~minutes and 19.95~seconds to complete the Rust setup. Throughout the process, Student~B reported feeling overwhelmed by the dense terminal output emitted by the \texttt{rustup} installer and consequently skimmed past the post-installation instructions printed to the console. As a result, Student~B failed to restart the terminal session or reload the shell configuration as instructed by the installer output, and expressed confusion when presented with information regarding the \texttt{PATH} environment variable and shell profile files.

In the declarative Nix Flake trial, Student~B completed the environment setup in 7~minutes and 6.64~seconds, an increase of 1~minute and 46.69~seconds over the imperative trial due to the initial Nix installer and \texttt{devShell} realization overhead. Unlike Student~A, however, Student~B preferred the traditional imperative installation method, explaining that the conventional step-by-step installer instructions felt more familiar and conceptually easier to follow than the unfamiliar Nix workflow.

As illustrated in Figure~\ref{fig:rq3-onboarding-results} and Figure~\ref{fig:rq3-avg-time-delta}, declarative activation via \texttt{nix develop} incurred a net time overhead compared to imperative installation across most trials (averaging +1:03.30 for Rust, +0:15.96 for Jupyter Notebook, and +2:09.21 for the Full Stack environment). This difference was driven primarily by the one-time installation of the Nix package manager and the initial realization of dependency store paths on clean virtual machines.

Nevertheless, comparing the single-toolchain Rust setup against the multi-component Jupyter Notebook and Full Stack environments partially supports Hypothesis~\textbf{H\textsubscript{3}}. As environment complexity increased from a single compiler to an integrated full-stack stack, the declarative time overhead narrowed from +1:33.64 to +0:40.27 for Student~A and from +1:46.69 to +1:28.55 for Student~B. In addition, Student~C completed the Rust trial 10.43\,s faster and Student~A completed the Jupyter trial 1~minute and 17.29\,s faster using \texttt{nix develop}, demonstrating that single-command activation becomes increasingly more favorable as manual installation procedures grow in complexity.

At the conclusion of the evaluation protocol, both Student~A and Student~B reported an overall preference for the imperative installation workflow. Although Student~A appreciated the simplicity of a single-command deployment, they noted that the automated shell realization felt like an opaque ``black box'' that obscured underlying environment state. Student~A reasoned that if an error occurred due to the configuration file or with Nix itself, they would lack the diagnostic visibility required to isolate the failure and independently remediate the issue. In contrast, while Student~C remained largely indifferent between the two choices, they favored the declarative Nix approach because it abstracted away low-level system configuration procedures, preventing learners from becoming entangled in protracted host troubleshooting cycles unrelated to core coursework objectives.
