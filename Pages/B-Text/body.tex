\section{Research Questions and Hypotheses}
\label{sec:rqs}

Building on the two research questions introduced in Chapter~\ref{chap:intro} and
the technical foundations established in Chapter~\ref{chap:litreview}, this
section defines the working hypotheses used to test each question. Specifically,
we map automated flake synthesis (\textbf{RQ1}) and cross-platform clean-environment
reproducibility (\textbf{RQ2}) to three testable hypotheses that guide our empirical
evaluation:
\begin{itemize}
	\item \textbf{H\textsubscript{1a} (RQ1):} Providing our custom agent skill (\texttt{course-flake-generator})
	      and closed-loop evaluation (\texttt{nix flake check}) will enable both
	      frontier (\texttt{Gemini 3.8 Flash}) and smaller open-weight (\texttt{GPT-OSS
		      120B}) models to reliably synthesize valid \texttt{flake.nix} environments,
	      narrowing the synthesis accuracy gap between model tiers.

	\item \textbf{H\textsubscript{1b} (RQ1):} Augmenting the agent with
	      structured package lookup via the \texttt{mcp-nixos} MCP server will reduce
	      package hallucinations and improve first-attempt synthesis accuracy (Pass@1)
	      and package precision compared to relying on training data knowledge and native
	      Nix CLI commands alone.

	\item \textbf{H\textsubscript{2} (RQ2):} Nix Flake environments that pass
	      the host validation pipeline with a pinned \texttt{flake.lock} will deterministically
	      reproduce and support coursework execution in clean, unmounted Linux
	      containers and macOS virtual machines, with any residual failures isolated
	      to platform-specific package availability.
\end{itemize}

\section{Proposed Solution: An Agent Skill for AI-Assisted Nix Flake Synthesis}
\label{chap:solution}

To bridge the gap between complex declarative configurations and educational
usability, we propose a custom agent skill that specializes an autonomous coding agent
in synthesizing and verifying valid \texttt{flake.nix} specifications. Rather than
requiring instructors or students to master the Nix expression language, the
skill delegates dependency inference and build verification to the user's local
agent harness. Although existing tools such as \texttt{devenv} introduced an AI-assisted
\texttt{devenv generate} command in version~1.4, that approach requires the
installation of \texttt{devenv} tool and subsequently had its CLI codebase-inference
capability removed following privacy concerns over telemetry that uploaded tracked
repository files to external servers~\cite{goodingDevenvFacesBacklash2025}. In
contrast, our proposed skill operates directly within the local agent harness to produce
standard \texttt{flake.nix} configurations while inspecting project repositories
and course documents locally.

Operating this synthesis pipeline requires a host environment that satisfies
three baseline prerequisites. First, the host system must run a POSIX-compatible
environment supported by the Nix package manager: Linux (natively or within
Docker containers), macOS, or Microsoft Windows via the Windows Subsystem for Linux
(WSL2). Second, Nix must be installed with experimental Flake support enabled.
When using the official Nix installer, users must explicitly enable flakes by declaring
\texttt{experimental-features = nix-command flakes} in either the user-level (\texttt{\textasciitilde/.config/nix/nix.conf})
or system-wide (\texttt{/etc/nix/nix.conf}) configuration file; alternatively,
the Determinate Systems Nix installer enables these features by default without
manual intervention. Third, a compatible agent harness must be installed to load
the skill package and orchestrate tool execution. Because Agent Skills follow an open,
modular specification consisting of structured Markdown instructions (\texttt{SKILL.md}),
reference templates, and helper scripts~\cite{AgentSkills,lingAgentSkillsDataDriven2026},
our skill is portable across any agent harness that supports the standard skill
directory convention and local shell tool invocation.

Operating through the instructor's local agent harness, the custom agent skill guides
an assignment-to-flake workflow (illustrated at a high level in Figure~\ref{fig:pipeline-overview})
across six sequential stages. Each stage enforces explicit validation boundaries
to ensure that only verified configurations progress toward student deployment:
\begin{enumerate}
	\item \textbf{Assignment document:} The instructor supplies existing
	      coursework materials (such as an assignment handout in DOCX, HTML, or Markdown
	      format, natural language instructions, or an unconfigured starter codebase)
	      without needing to manually compose Nix expressions.

	\item \textbf{Requirement extraction:} The agent extracts required compilers,
	      language runtimes, build tools, and system libraries from the provided materials.
	      This capability is driven by the custom skill's bundled scripts: a document
	      extraction script to parse unstructured assignment handouts, alongside a
	      project detector that scans codebase files and documentation for the
	      appropriate runtime runtimes and dependencies, similar to how \cite{schwaighoferVibenixAIAssistant2026}
	      analyzes a project.

	\item \textbf{Flake generation:} Guided by the \texttt{course-flake-generator}
	      skill's multi-architecture templates and reference heuristics, the agent
	      synthesizes a declarative \texttt{flake.nix} specification. To resolve
	      required package attributes deterministically, the skill primarily queries
	      the \texttt{mcp-nixos} server against real-time Nixpkgs search indices, falling
	      back to native Nix CLI inspection commands when the MCP server is not present.

	\item \textbf{Validation:} The candidate \texttt{flake.nix} is evaluated through
	      closed-loop verification, executing \texttt{nix flake check} and ephemeral
	      shell realization checks to detect syntax errors or missing executables.
	      If failures occur, compiler diagnostics are returned to the agent harness
	      for automated self-correction until validation passes and generates a pinned
	      \texttt{flake.lock}.

	\item \textbf{Instructor approval:} The instructor reviews the synthesized
	      \texttt{flake.nix} and cryptographically pinned \texttt{flake.lock} file
	      and commits them to the assignment repository, establishing a verified,
	      frozen dependency closure for the course.

	\item \textbf{Student activation:} Students clone the assignment repository
	      onto their personal devices and run \texttt{nix develop} to enter the reproducible
	      development shell, avoiding manual installation troubleshooting and
	      working directly on the assignment.
\end{enumerate}

\section{Agentic Flake Synthesis Evaluation Protocol}
\label{sec:rq1-methodology}

To investigate whether modern autonomous agents can reliably synthesize
declarative Nix development environments from informal natural language
requirements (RQ1), we established a benchmark evaluation protocol. This
protocol couples structured curriculum task suites with an automated
verification pipeline to measure synthesis accuracy, dependency resolution, and
runtime execution determinism.

\subsection{Benchmark Dataset Curation and Evaluation Suites}
\label{subsec:dataset-curation}

Because standardized benchmark datasets for declarative Nix environments did not previously
exist, we assembled an evaluation benchmark representing computer science
coursework requirements across three distinct instructional modalities. These modalities
combine synthetic natural language prompts inspired by the author's knowledge of and
experience in various repositories and instructional handouts collected from university
computer science courses:

\begin{enumerate}
	\item \textbf{Natural Language Specification Prompts:} Artificially created
	      prompts modeled after the author's personal experience across
	      undergraduate and graduate computer science courses, organized into two curriculum
	      tracks:
	      \begin{itemize}
		      \item \emph{Computer Science Track:} Assignments focusing on systems
		            programming, compiler toolchains, mobile and desktop application
		            development, and web engineering. These tasks require native
		            compilers, build systems, and runtime interpreters, including Java
		            (JDK~17, VS~Code), Flutter and Dart, Python (with \texttt{uv}),
		            C/C++ (GCC, Clang, CMake, GNU Make), Node.js, Rust (\texttt{rustup},
		            Cargo, \texttt{rustc}), Go, the .NET SDK, and Ruby (with Bundler).

		      \item \emph{Data Science Track:} Coursework requiring statistical
		            computing environments and relational database management tools, including
		            R statistical environments, RStudio Desktop, MySQL Server, and
		            MySQL Workbench.
	      \end{itemize}
	      The prompt benchmark is serialized as a \texttt{jsonl} file, where each
	      record specifies the curriculum track, the natural language prompt, and
	      the asserted dependency list (Listing~\ref{lst:input-data-format}; the
	      complete prompt suite is provided in Appendix~\ref{apd:a},
	      Listing~\ref{lst:nl-instruction-inputs}).

	\item \textbf{Existing Coursework Codebases:} A collection of real-world
	      assignment codebases from the author's undergraduate computer science
	      courses spanning artificial intelligence, Java, Swift, neural networks,
	      and network programming. For these tasks, the agent cannot rely on
	      explicit textual package lists; instead, the skill instructs the agent
	      to run \texttt{detect-project-requirements.py} to inspect file contents,
	      repository structures, and build manifests (such as \texttt{pom.xml},
	      \texttt{build.gradle}, and \texttt{pyproject.toml}) to infer the
	      necessary runtimes and dependencies.

	\item \textbf{Instructional Course Documents:} A collection of six real-world
	      course documents and laboratory setup guides packaged as Microsoft Word
	      (\texttt{.docx}), HTML, and Markdown \texttt{README} files. To process these
	      unstructured documents, the skill executes \texttt{extract-document-content.py}
	      to parse layout structures into clean text for agent requirement extraction
	      using the \texttt{docling}\cite{researchDoclingGetYour2024} Python package.
\end{enumerate}

To establish an objective evaluation standard across all three modalities, each task
is paired with an evaluation schema defining human defined ground-truth requirements.
While synthetic prompt benchmarks are serialized as a unified \texttt{jsonl} file,
each codebase directory and instructional document is paired with an individual
companion metadata \texttt{.json} file (Listing~\ref{lst:input-data-format}).
Across modalities, validation requirements match the nature of the input:
natural language specification prompts and instructional course documents are
validated against \texttt{dependency\_list}, whereas existing coursework
codebases are validated against both \texttt{dependency\_list} and an executable \texttt{verification\_command}
that compiles or executes the repository's source files inside the synthesized
environment.

\begin{lstlisting}[caption={Evaluation Metadata Format and Ground-Truth Schema}, label={lst:input-data-format}]
{
  "track": "computer science",
  "instruction": "Set up a Nix flake development environment...",
  "dependency_list": [
    "emacs"
  ],
  "verification_command": "emacs --batch -Q -f batch-byte-compile src.el && rm -f src.elc"
}
\end{lstlisting}

In this schema, \texttt{track} classifies the curriculum domain, \texttt{title} and
\texttt{instruction} provide contextual task descriptions, \texttt{dependency\_list}
designates the ground-truth executables that must resolve inside the \texttt{nix
	develop} shell across all three modalities, and \texttt{verification\_command} specifies
the codebase-level shell command used to verify that project source files compile
or interpret cleanly within the synthesized environment. The automated
evaluation harness evaluates these human-verified assertions to determine
whether candidate flakes satisfy the Pass@$k$ criteria and to compute package precision
and over-provisioning metrics. Table~\ref{tab:coursework-codebases} and Table~\ref{tab:coursework-documents}
detail the complete suites of curated coursework codebases and instructional
setup documents evaluated under this schema alongside their descriptions and
dependencies.

\subsection{Agent Harness, Model Configurations, and Tooling Conditions}
\label{subsec:agent-harness}

The experimental synthesis harness was implemented using the Antigravity CLI harness.
This harness coordinates prompt delivery, tool routing, and shell execution
streaming.

We also wanted to assess how model architecture and parameter size influence Nix
flake synthesis, experiments were conducted across two language models: Google
Gemini~3.8 Flash and GPT-OSS 120B, both configured with medium reasoning effort within
the antigravity cli harness. Evaluating models across different parameter scales
allows us to assess whether smaller, cost-effective models can synthesize functionally
equivalent environments when equipped with the agent skill.

To evaluate the impact of domain-specific procedural scaffolding against unassisted
zero-shot generation, our primary RQ1 comparison evaluates both models under two
conditions: \textbf{No Skill} (baseline agent harness without custom Nix scaffolding)
and \textbf{Skill} (agent harness equipped with our specialized \texttt{course-flake-generator}
skill introduced in Section~\ref{chap:solution}). The internal filetree structure
of the custom agent skill follows standardized agentic skill packaging conventions:

\begin{lstlisting}[caption={Custom Skill Filetree Structure}, label={lst:custom-skill-filetree}]
.
├── README.md
├── SKILL.md
├── assets
│   ├── flake-devshell.template.nix
│   └── mcp-servers.template.json
├── references
│   ├── flake-patterns.md
│   ├── inferring-requirements.md
│   └── mcp-nixos.md
└── scripts
    ├── detect-project-requirements.py
    ├── extract-document-content.py
    └── validate-flake.py

\end{lstlisting}

The \texttt{assets/} directory bundles validated boilerplate templates for \texttt{devShells}
across multi-architecture systems. Similar to the templates evaluated by Schwaighofer
et~al.~\cite{schwaighoferVibenixAIAssistant2026}, placeholder values are indicated
by \texttt{\{\{\}\}}, adopting Jinja2 templating notation. The \texttt{references/}
directory supplies documentation outlining common Nix idiomatic patterns and troubleshooting
heuristics. The \texttt{scripts/} directory stores Python scripts to perform deterministic
actions such as extracting text from user submitted documents. According to Ling
et~al.~\cite{lingAgentSkillsDataDriven2026}, providing modular templates
significantly improves behavioral consistency and task adherence in autonomous
agents.

\begin{lstlisting}[caption={\texttt{assets/flake-devshell.template.nix} Template}]

            {{PACKAGES}}
          ];

          {{ENV_VARS}}

          shellHook = ''

          '';
        };

        formatter = pkgs.nixfmt-rfc-style;
      }
    );
}

\end{lstlisting}

Additionally, as an ablation study on top of the skill-equipped agent, we evaluated
two distinct package discovery conditions to measure the impact of external tool grounding.
Comparing these configurations isolates whether autonomous agents strictly
require external registry access or can reliably synthesize environments using
native command-line tools alone:
\begin{enumerate}
	\item \textbf{Live Registry Retrieval via MCP-NixOS:} The agent queries the
	      \texttt{mcp-nixos} server, which communicates directly with the
	      Elasticsearch index powering \texttt{search.nixos.org}. Because Nixpkgs
	      hosts over 139,008 packages across 1,044 package sets, real-time index querying
	      protects against package hallucinations, deprecated attribute paths, and naming
	      drift~\cite{borkLanguageServerProtocol2023,ImportingPhantomsMeasuring}.

	\item \textbf{Native Nix CLI Discovery:} In this condition, the MCP server is
	      withheld from the agent, forcing it to rely exclusively on parametric
	      pre-training weights and native Nix command-line inspection tools (such as
	      \texttt{nix search} and \texttt{nix-env -qaP}).
\end{enumerate}

An automated Python test runner was developed to execute test suites, capture agent
tool call telemetry, stream shell outputs, and record execution success metrics.
The runner logs detailed traces for every trials to perform detailed analysis.

The artifacts generated within each benchmark serve distinct functions for performance
aggregation, behavioral auditing, and trial verification. These files capture
telemetry across multiple levels of granularity, enabling post evaluation analysis:

\begin{itemize}
	\item \texttt{benchmark\_summary.json}: Aggregates Pass@$k$ metrics, execution
	      latency, token consumption, and dependency bloat scores across all trials.
	      It serves as the primary machine-readable dataset for statistical
	      analysis.

	\item \texttt{benchmark\_report.md}: Summarizes benchmark results, per-task
	      score tables, and execution parameters in Markdown format. It provides
	      an immediate overview of benchmark outcomes and links to individual
	      agent sessions.

	\item \texttt{tool\_call\_frequency.csv}: Records the overall frequency,
	      trial prevalence, and average invocations of every agent tool call. It
	      quantifies how agent tool usage shifts between different model and
	      grounding conditions.

	\item \texttt{tool\_call\_frequency\_by\_task.csv}: Cross-tabulates tool calls
	      across individual coursework assignments, revealing which problem
	      domains introduced heavier tool utilization.

	\item \texttt{tool\_call\_frequency\_by\_trial.csv}: Maps tool invocations at
	      the level of individual trial samples alongside validation success and duration,
	      facilitating fine-grained correlation between tool call patterns and
	      task outcomes.

	\item \texttt{run\_command\_frequency.csv} and \texttt{run\_command\_base\_frequency.csv}:
	      Tabulate exact and base shell commands executed through the agent
	      harness. They reveal the CLI inspection patterns and build utilities invoked
	      during synthesis.

	\item \texttt{run\_command\_log.csv}: Logs a complete, timestamped
	      chronological trace of every shell command executed, its working directory,
	      and associated metadata.

	\item \texttt{mcp\_tool\_frequency.csv} and \texttt{mcp\_tool\_log.csv}:
	      Capture all registry search queries, filter arguments, and actions
	      dispatched to the mcp server, if applicable.

	\item \texttt{agent\_response.md}: Preserves the final conversational completion
	      message and instructions returned by the agent. It allows evaluators to
	      verify the clarity and correctness of the agent's onboarding guidance.

	\item \texttt{flake.lock}: Pins exact cryptographic source hashes and input commits
	      generated during local validation. It guarantees reproducible, deterministic
	      evaluation across clean guest environments.

	\item \texttt{flake.nix}: Defines the declarative \texttt{devShell}
	      environment and package inputs synthesized by the agent. It is the primary
	      artifact tested against the three-stage validation pipeline.

	\item \texttt{raw\_output.log}: Captures unbuffered standard output and standard
	      error streams from the agent harness execution. It assists with post-mortem
	      debugging whenever an execution hangs or crashes unexpectedly.

	\item \texttt{transcript.jsonl}: Stores the comprehensive turn-by-turn event stream,
	      including internal reasoning traces, tool parameters, and raw tool
	      responses. It provides full behavioral provenance for qualitative evaluation.

	\item \texttt{trial\_meta.json}: Records structured trial execution metrics,
	      including pass/fail status, validation stages completed, latency, token usage,
	      and dependency precision. It supplies the ground-truth values used to calculate
	      Pass@$k$ and bloat statistics.
\end{itemize}

\subsection{Three-Stage Validation Pipeline and Pass@K Formulation}
\label{subsec:pass-k-metric}

Synthesizing a declarative \texttt{flake.nix} file requires navigating a
functional domain-specific language where surface syntactic correctness does not
guarantee runtime deployability~\cite{zhangDeployabilityCentricInfrastructureasCodeGeneration2025}.
To rigorously verify that generated environments are functional, every candidate
flake must satisfy a three-stage automated validation pipeline:
\begin{enumerate}
	\item \textbf{Syntax and Evaluation Validity:} The command \texttt{nix flake
		      check} evaluates the generated \texttt{flake.nix} with lock-file writes
	      disabled, ensuring that the expression parses cleanly without syntax errors,
	      missing attributes, or invalid type signatures.

	\item \textbf{Build and Realization Determinism:} The command \texttt{nix
		      develop --command <test-cmd>} successfully enters the ephemeral shell and
	      resolves all declared binaries on the \texttt{PATH}.

	\item \textbf{Functional Task Execution:} The assignment source code builds
	      and passes its unit test suite inside the synthesized \texttt{devShell},
	      verifying that compiler toolchains and runtime headers interact
	      correctly with project source files.
\end{enumerate}

To quantify synthesis reliability, we adapted the Pass@$k$ formulation from code
generation literature~\cite{chenEvaluatingLargeLanguage2021}. Pass@$k$ measures
the probability that at least one of $k$ generated candidate environments passes
all validation stages, where we generate $n \ge k$ samples per task. For our
evaluation, we set $k = 3$ and $n = 3$.

This formulation calculates the probability that an instructor obtains at least one
working environment without having to evaluate every trial sequentially.
Specifically, we calculate Pass@$k$ using the unbiased estimator introduced by
Chen et~al.~\cite{chenEvaluatingLargeLanguage2021}:
\[
	\mathrm{pass@}k := \underset{\text{Problems}}{\mathrm{E}}\left[ 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}
		\right]
\]
where $n$ is the total number of generated candidate samples per task and $c$ is
the number of samples that successfully pass all three validation stages.

\section{Clean-Environment Reproducibility Protocol}
\label{sec:rq2-methodology}

RQ2 evaluates whether a successful local validation actually transfers to a fresh
environment without any configurations. The inputs contain only RQ1 trial
artifacts that passed the three-stage local verifier and include both a
generated \texttt{flake.nix} and its \texttt{flake.lock}. This design evaluates the
reproducibility of the generated flake specification.

On a local development machine, an existing Nix store or globally installed host
library may mask missing dependency declarations, creating a false impression of reproducibility.
To isolate the environment away from the hosts' machine, our test mandates that
candidate flakes be tested in fresh, ephemeral guest environments where no host directories
or store paths are mounted.

The harness streams a compressed copy of the trial into the guest environment and
extracts it into guest-local temporary storage; no project directory or host Nix
store is mounted. The guest instance is discarded when the stage finishes, so no
writable state is shared across stages or trials. Network access remains available
so that a first-use environment can retrieve its pinned inputs and binary-cache artifacts,
and availability failures are recorded separately from configuration failures.

\subsection{Guest Replay Pipeline and Failure Taxonomy}

The guest-side verifier executes four sequential stages on each RQ1-passing artifact.
These stages mirror the host verification harness while preventing unstated host
assumptions from masquerading as portable configurations:
\begin{enumerate}
	\item \textbf{Locked Flake Evaluation:} \texttt{nix flake check} evaluates the
	      generated flake with lock-file writes disabled.

	\item \textbf{Development-Shell Activation:} \texttt{nix develop --command
		      true} verifies that the development shell can be activated.

	\item \textbf{Required Tool Availability:} Each executable listed in the
	      original RQ1 dependency assertion is checked with \texttt{command -v} inside
	      the development shell.

	\item \textbf{Headless Task Execution:} A curated per-task command set
	      verifies applicable language runtimes, builds, dependency
	      synchronization, or test commands. Graphical editor workflows, interactive
	      credentials, and persistent database-service administration are excluded
	      because they cannot be assessed consistently by a headless guest.
\end{enumerate}

The principal metric is the base OS reproduction rate: the proportion of trials that
complete every applicable guest-side stage. Failures are classified as flake-evaluation
failures, shell-activation failures, missing dependencies, functional task failures,
or infrastructure failures (unsupported CPU architecture). For each trial, the
harness records the source identifier, guest image digest and system architecture,
command exit codes, standard output and error logs, and stage durations, making it
possible to distinguish a defective generated environment from a transient guest or
upstream package-source failure.

To evaluate cross-platform reproducibility across the different platforms used by
students, the RQ2 replay pipeline executes across two isolated guest
virtualization environments:
\begin{itemize}
	\item \textbf{Linux Replay Containers:} To simulate standard Linux and
	      Windows Subsystem for Linux (WSL) environments, validation stages are replayed
	      inside unmounted Docker containers running official Nix images. Each
	      trial executes in an isolated container lifecycle without shared
	      filesystem volumes or pre-warmed host store paths.

	\item \textbf{macOS Tart Virtual Machines:} To evaluate macOS and Apple
	      Silicon guest environments, we utilize Tart, an open-source
	      virtualization framework optimized for Apple Silicon hypervisors. We obtained
	      a clean image of macOS Golden Bridge via \texttt{ghcr.io/cirruslabs/macos-golden-gate-base:latest
		      macos-27-base}.
\end{itemize}

Transcript inspection explains why \texttt{mcp-nixos} yields no accuracy
advantage over native CLI discovery: both interfaces query and return the exact same
underlying Nixpkgs package metadata. When MCP access was withheld, the skill directed

trials reaching the 900-second execution timeout prior to emitting transcript
logs). Within these analyzed trials, \texttt{Gemini 3.8 Flash} utilized MCP
lookup consistently, averaging 3.40 calls per trial across all 40 runs. In
contrast, \texttt{GPT-OSS 120B} invoked \texttt{mcp-nixos} only 6 times across 3 of
41 analyzed trials (0.15 calls/trial) because it began 58.54\% of its trials (24/41)
by calling \texttt{list\_resources}, misinterpreted the empty static resource
list returned by the tool-only MCP server as an absence of capabilities.

carries a practical advantage for classroom deployment. In line with recent findings

CLI scaffolding often matches or outperforms specialized external tool servers, our
ablation study confirms that instructors do not need to install, configure, or maintain
an external MCP server. The standalone \texttt{course-flake-generator} skill and standard
Nix CLI commands are sufficient on their own to achieve 95\%--100\% synthesis
accuracy.
\section{Base OS Reproducibility Results}
\label{sec:base-os-results}

The base operating system replay evaluation investigated the cross-platform
reproducibility of eligible artifacts that passed host-side validation during
the RQ1 synthesis benchmark. Each passing \texttt{flake.nix} and corresponding
lockfile was evaluated across two isolated, clean environments: disposable Linux
Docker containers running on an unprivileged host architecture and clean macOS
virtual machines managed via the Tart virtualization framework. Replay trials executed
an automated four-stage verification pipeline matching the guest replay protocol:
static flake syntax check (\texttt{flake\_check}), development shell realization
and hook execution (\texttt{activation}), binary presence verification on
\texttt{PATH} for every declared dependency (\texttt{missing\_dependency}), and headless
task command verification (\texttt{task\_<index>}). Replay outcomes were systematically
classified according to the taxonomy implemented in \texttt{replay\_clean\_docker.py},
separating packaging errors from runtime functional execution errors.

Figure~\ref{fig:rq2-linux-results} and Figure~\ref{fig:rq2-macos-results} present
the clean replay outcomes across the Computer Science and Data Science curriculum
tracks for Linux and macOS, respectively. Across both operating systems, the
generated flakes demonstrated robust structural isolation: zero trials encountered
\texttt{flake\_failure}, \texttt{activation\_failure}, or \texttt{missing\_dependency}.
In every instance, the Nix evaluator built the requested development shell
derivation, populated the store paths, executed shell hooks without fatal exit
codes, and placed all required tool binaries on the active \texttt{PATH}. Nevertheless,
a subset of trials experienced \texttt{functional\_failure}, wherein the
environment successfully activated with all dependencies present, but task-specific
headless test commands exited with non-zero status codes.

In the Linux container replay (Figure~\ref{fig:rq2-linux-results}), 34 of the 41
eligible trials reproduced successfully without manual intervention, achieving an
overall clean reproduction rate of 82.9\%. Across curriculum tracks, the
Computer Science track achieved an 83.3\% reproduction rate (25 reproduced, 5 functional
failures out of 30 trials), while the Data Science track achieved an 81.8\%
reproduction rate (9 reproduced, 2 functional failures out of 11 trials). In the
clean macOS virtual machine replay (Figure~\ref{fig:rq2-macos-results}), 39 of the
41 eligible trials reproduced successfully, yielding a 95.1\% overall clean reproduction
rate. Specifically, the Computer Science track attained 93.3\% reproducibility (28
reproduced, 2 functional failures out of 30 trials), while the Data Science
track achieved 100.0\% reproducibility (11 reproduced, 0 functional failures out of
11 trials).

Detailed post-mortem analysis of the trial logs revealed that all seven Linux
failures and both macOS failures stemmed from three distinct root causes within
the \texttt{functional\_failure} classification. Crucially, none of these failures
reflect a defect in Nix's reproducibility model or the syntax of the generated flake
files; rather, they arise from the runtime behavior of the installed applications
and the constraints of the headless testing environment:

\begin{enumerate}
	\item \textbf{Container Privilege Boundaries and Electron Headless
		      Sandboxing:} In the Linux Docker replay environment, all trials for the code
	      editor environment failed during the headless verification of Visual Studio
	      Code (\texttt{code --version}). The containerized replay harness executed
	      inside disposable, headless Docker containers operating under the
	      superuser (\texttt{root}) account. Visual Studio Code, built on the Electron
	      framework, enforces a strict sandboxing policy that rejects execution
	      under root privileges in headless Linux environments without explicit
	      runtime flags, terminating immediately with the diagnostic: \textit{"You are
		      trying to start Visual Studio Code as a super user which isn't recommended.
		      If this was intended, please add the argument --no-sandbox and specify an
		      alternate user data directory using the --user-data-dir argument."} In contrast,
	      local host verification executed under a standard unprivileged user
	      account, allowing \texttt{code --version} to exit cleanly. Similarly, on
	      the clean macOS Tart virtual machines, the evaluation runner operated under
	      the unprivileged \texttt{admin} user, where Darwin application bundles do
	      not enforce Linux-specific container sandbox restrictions; as a result, all
	      corresponding trials reproduced cleanly on macOS.

	\item \textbf{Host Machine Pollution During Verification:} Across both Linux
	      and macOS, multiple trials failed during the compiler verification command
	      (\texttt{rustc --version \&\& cargo --version}) for the Rust toolchain
	      environment. When synthesizing the development environment from prompt instructions
	      requiring \texttt{rustup}, the agent declared the Nixpkgs derivation \texttt{pkgs.rustup}
	      in \texttt{buildInputs}. In Nixpkgs, the \texttt{rustup} package
	      provides proxy shims for \texttt{rustc} and \texttt{cargo} that
	      dynamically resolve to toolchains managed under the user's mutable home
	      directory (\texttt{\$HOME/.rustup}). On the author's MacBook, \texttt{\textasciitilde/.rustup}
	      already existed, prompting the model to exclude \texttt{rustup default
		      stable} within the flake.nix file. When deployed to fresh guest environments
	      where \texttt{\$HOME/.rustup} was empty, calling \texttt{rustc} failed
	      with the diagnostic: \textit{"error: rustup could not choose a version
		      of rustc to run, because one wasn't specified explicitly, and no default
		      is configured."} In contrast, one synthesized trial succeeded on both Linux
	      and macOS because the model included \texttt{rustup default stable}
	      inside the flake's \texttt{shellHook}, which automatically downloads (if missing)
	      and configures the stable versions of \texttt{rustc} and \texttt{cargo}
	      within the clean environment prior to command verification.

	\item \textbf{Absence of Display Server for Graphical Applications:} In the
	      Data Science track, trials for the database administration environment failed
	      during the verification command (\texttt{mysql-workbench --version})
	      during Linux container replay. MySQL Workbench is a desktop client application
	      compiled against GTK and X11 graphical libraries. When invoked inside
	      the headless Docker container, the binary attempted to initialize a connection
	      to a non-existent graphical display server, terminating with the runtime
	      fault: \textit{"(mysql-workbench-bin): Gtk-WARNING **: cannot open
		      display:"}. In the macOS virtual machine environment, Darwin application
	      binaries and command wrappers do not depend on an X11 display socket, allowing
	      all corresponding trials to execute without failure.
\end{enumerate}

These findings provide strong empirical validation for Hypothesis~\textbf{H\textsubscript{2}},
demonstrating that declarative Nix Flakes deliver high cross-platform
determinism (95.1\% on macOS and 82.9\% on Linux) with zero environment-realization
or missing-dependency failures. Crucially, the failure taxonomy confirms that
every observed failure stemmed from application-specific runtime assumptions or
test-harness constraints rather than broken Nix package realization. Five of the seven
observed failures on Linux, specifically those involving graphical applications, were
artifacts of the headless container test harness running under superuser privileges
and a display server; because student devices operate under unprivileged user
accounts with graphical desktop sessions, these container-specific constraints do
not reflect real world student onboarding. Similarly, the failures observed during
the Rust toolchain replay stemmed from \texttt{rustup}'s design as a stateful, user-directory
toolchain manager whose uninitialized state was masked on the authoring host's machine
by an existing \texttt{\textasciitilde/.rustup} cache.
