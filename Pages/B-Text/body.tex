\chapter{Research Questions and Proposed Architecture}\label{RQ}

\section{Research Questions and Hypotheses}\label{sec:rqs}

This thesis investigates the feasibility, reproducibility, and reliability of automated declarative environment generation for computer science education. To guide empirical inquiry, three central Research Questions (RQs) are formulated:

\rqlist

To evaluate these questions systematically, we formulate four corresponding working hypotheses:
\begin{itemize}
	\item \textbf{H\textsubscript{1a}:} Providing structured procedural scaffolding (\texttt{course-flake-generator}) and closed-loop evaluation (\texttt{nix flake check}) will enable both frontier (\texttt{Gemini 3.8 Flash}) and smaller open-weight (\texttt{GPT-OSS 120B}) models to reliably synthesize valid \texttt{flake.nix} environments, narrowing the synthesis accuracy gap between model tiers.
	\item \textbf{H\textsubscript{1b}:} Augmenting the agent with real time data (\texttt{mcp-nixos}) will reduce package hallucinations and improve first-attempt synthesis accuracy (Pass@1) and package precision compared to relying on training data knowledge and native Nix CLI commands alone.
	\item \textbf{H\textsubscript{2}:} Nix Flake environments that pass the three-stage host validation pipeline with a pinned \texttt{flake.lock} will deterministically reproduce and support headless coursework execution in clean, unmounted Linux containers and macOS virtual machines, with any residual failures isolated to undeclared native build inputs or platform-specific package availability.
	\item \textbf{H\textsubscript{3}:} Single-command activation via \texttt{nix develop} will reduce procedural errors and cognitive friction compared to manual imperative installation.
\end{itemize}

\section{Proposed Solution: An agent skill for AI-Assisted Nix Flake Synthesis}\label{chap:solution}

To bridge the gap between complex declarative configurations and educational usability, we propose a custom agent skill that specializes an autonomous coding agent in synthesizing and verifying valid \texttt{flake.nix} specifications. Rather than requiring instructors or students to master the Nix expression language, the skill delegates dependency inference, package resolution, and build verification to the user's local agent harness. Although existing wrapper ecosystems such as \texttt{devenv} introduced an AI-assisted \texttt{devenv generate} command in version~1.4, that approach requires the installation of \texttt{devenv} tool and subsequently had its CLI codebase-inference capability removed following privacy concerns over telemetry that uploaded tracked repository files to external servers~\cite{goodingDevenvFacesBacklash2025}. In contrast, our proposed skill operates directly within the local agent harness to produce standard, zero-wrapper \texttt{flake.nix} configurations while inspecting project repositories and course documents locally.

Operating this synthesis pipeline requires a host environment that satisfies three baseline prerequisites. First, the host system must run a POSIX-compatible environment supported by the Nix package manager: Linux (natively or within Docker containers), macOS, or Microsoft Windows via the Windows Subsystem for Linux (WSL2). Second, Nix must be installed with experimental Flake support enabled. When using the official Nix installer, users must explicitly enable flakes by declaring \texttt{experimental-features = nix-command flakes} in either the user-level (\texttt{\textasciitilde/.config/nix/nix.conf}) or system-wide (\texttt{/etc/nix/nix.conf}) configuration file; alternatively, the Determinate Systems Nix installer enables these features by default without manual intervention. Third, a compatible agent harness must be installed to load the skill package and orchestrate tool execution. Because Agent Skills follow an open, modular specification consisting of structured Markdown instructions (\texttt{SKILL.md}), reference templates, and helper scripts~\cite{AgentSkills,lingAgentSkillsDataDriven2026}, our skill is portable across any agent harness that supports the standard skill directory convention and local shell tool invocation.

The end-to-end architecture comprises the following steps (illustrated at a high level in Figure~\ref{fig:pipeline-overview}):
\begin{enumerate}
	\item \textbf{Requirement Ingestion:} Specifications from natural language, existing codebases, or instructional documents on setting up compute environments are analyzed to extract inferred toolchains, language runtimes, and system-level libraries. To accurately retrieve requirements from unstructured course documents, a Python script is bundled alongside the skill that leverages the Docling \cite{Docling} package to parse out text for the agent to use as context.
	\item \textbf{Specialized Agent Skill Scaffolding and Live Package Retrieval:} The custom agent skill provides domain-specific prompting, curated templates, and reference schemas. The skill also provides the agent the proper command to query a Model Context Protocol (MCP) server that reaches out to real time nix search indices.
	\item \textbf{Deterministic Closed-Loop Verification:} Generated \texttt{flake.nix} files are evaluated via native Nix commands such as \texttt{nix flake check}, which statically checks the generated flake configuration. If syntax or dependency errors occur, the compiler diagnostics are fed back into the agent harness for iterative self-correction.
	\item \textbf{Output Artifacts and Runtime Deployment:} A cryptographically pinned \texttt{flake.lock} file is generated from \texttt{nix flake check}, allowing students to activate a reproducible developer shell.
\end{enumerate}

\section{Agentic Flake Synthesis Evaluation Protocol}\label{sec:rq1-methodology}

To investigate whether modern autonomous agents can reliably synthesize declarative Nix development environments from informal natural language requirements (RQ1), we established a benchmark evaluation protocol. This protocol couples structured curriculum task suites with an automated verification pipeline to measure synthesis accuracy, dependency resolution, and runtime execution determinism.

\subsection{Benchmark Dataset Curation and Curriculum Tracks}\label{subsec:dataset-curation}

Because standardized benchmark datasets for declarative Nix environments did not previously exist, we constructed an evaluation benchmark representing standard computer science coursework requirements. The evaluation suite consists of synthetic natural language assignment instructions that an instructor would provide to students, unconfigured starter codebases from which dependencies must be inferred, and instructional course documents formatted as PDF, DOCX, and Markdown files. The evaluation tasks are organized across two distinct curriculum tracks:
\begin{enumerate}
	\item \textbf{Software Development Track:} Curated assignments focusing on systems programming, compiler toolchains, and web engineering. These tasks require native compilers, build systems, and runtime interpreters, including C/C++ (GCC, Clang, CMake, GNU Make), Rust (Cargo, \texttt{rustc}), and full-stack environments (Python, Node.js).
	\item \textbf{Data Science Track:} Curated coursework requiring complex scientific computing stacks, numeric routines, and specialized packages, including Python (NumPy, SciPy, Pandas, PyTorch), R statistical environments, and Jupyter notebook kernels.
\end{enumerate}

The benchmark dataset is serialized as a \texttt{jsonl} file, where each record specifies the curriculum track, the natural language prompt or project path, and the set of required dependencies asserted for verification:

\begin{lstlisting}[caption={Input Data Format}, label={lst:input-data-format}]
  {
    "track": "...",
    "instruction": "...",
    "dependency": "...",
  }
\end{lstlisting}

In this format, \texttt{track} classifies the curriculum category, \texttt{instruction} represents the natural language prompt or specification provided to the agent, and the \texttt{dependency} field specifies the list of packages or executables that must be present in \texttt{PATH} when \texttt{nix develop} is invoked to evaluate agent performance.

\subsection{Agent Harness, Model Configurations, and Tooling Conditions}\label{subsec:agent-harness}

The experimental synthesis harness was implemented using the Antigravity CLI harness. This harness coordinates prompt delivery, tool routing, and shell execution streaming.

We also wanted to assess how model architecture and reasoning scale influence Nix expression synthesis, experiments were conducted across two language models: Google Gemini~3.8 Flash and GPT-OSS 120B, both configured with medium reasoning effort. Evaluating models across different parameter scales allows us to assess whether smaller, cost-effective models can synthesize functionally equivalent environments when equipped with appropriate contextual scaffolding.

To guide the agent and eliminate erratic zero-shot behavior, each agent session integrates our specialized \texttt{course-flake-generator} skill (introduced in Section~\ref{chap:solution}). The internal filetree structure of the custom agent skill follows standardized agentic skill packaging conventions:

Additionally, we evaluated two distinct package discovery conditions:
\begin{enumerate}
	\item \textbf{Live Registry Retrieval via MCP-NixOS:} The agent queries the \texttt{mcp-nixos} FastMCP server, which communicates directly with the Elasticsearch index powering \texttt{search.nixos.org}. Because Nixpkgs hosts over 139,008 packages across 1,044 package sets, real-time index querying protects against package hallucinations, deprecated attribute paths, and naming drift~\cite{borkLanguageServerProtocol2023,ImportingPhantomsMeasuring}.
	\item \textbf{Native Nix CLI Discovery:} In this condition, the MCP server is withheld from the agent, forcing it to rely exclusively on parametric pre-training weights and native Nix command-line inspection tools (such as \texttt{nix search} and \texttt{nix-env -qaP}).
\end{enumerate}

An automated Python test runner was developed to execute test suites, capture agent tool call telemetry, stream shell outputs, and record execution success metrics. The runner logs detailed traces for every synthesis attempt to facilitate post-hoc telemetry analysis.

The artifacts generated within each benchmark run serve distinct functions for performance aggregation, behavioral auditing, and trial verification:

\begin{itemize}
	\item \texttt{benchmark\_summary.json}: Aggregates Pass@$k$ metrics, execution latency, token consumption, and dependency bloat scores across all trials. It serves as the primary machine-readable dataset for statistical analysis.
	\item \texttt{benchmark\_report.md}: Summarizes benchmark results, per-task score tables, and execution parameters in Markdown format. It provides an immediate overview of benchmark outcomes and links to individual agent sessions.
	\item \texttt{tool\_call\_frequency.csv}: Records the overall frequency, trial prevalence, and average invocations of every agent tool call. It quantifies how agent tool usage shifts between different model and grounding conditions.
	\item \texttt{tool\_call\_frequency\_by\_task.csv} and \texttt{tool\_call\_frequency\_by\_trial.csv}: Break down tool invocation distributions across specific tasks and individual trial samples. These matrices highlight task-specific variance and individual trial behavioral anomalies.
	\item \texttt{run\_command\_frequency.csv} and \texttt{run\_command\_base\_frequency.csv}: Tabulate exact and base shell commands executed through the agent harness. They reveal the CLI inspection patterns and build utilities invoked during synthesis.
	\item \texttt{run\_command\_log.csv}: Logs a complete, timestamped chronological trace of every shell command executed, its working directory, and associated metadata. 	
	\item \texttt{mcp\_tool\_frequency.csv} and \texttt{mcp\_tool\_log.csv}: Capture all registry search queries, filter arguments, and actions dispatched to the mcp server, if applicable.
	\item \texttt{agent\_response.md}: Preserves the final conversational completion message and instructions returned by the agent. It allows evaluators to verify the clarity and correctness of the agent's onboarding guidance.
	\item \texttt{flake.lock}: Pins exact cryptographic source hashes and input commits generated during local validation. It guarantees reproducible, deterministic evaluation across clean guest environments.
	\item \texttt{flake.nix}: Defines the declarative \texttt{devShell} environment and package inputs synthesized by the agent. It is the primary artifact tested against the three-stage validation pipeline.
	\item \texttt{jupyter\_install.html}: Contains the localized assignment specification or handout provided to the agent in document-grounded tasks. Isolating this input guarantees a self-contained trial workspace.
	\item \texttt{raw\_output.log}: Captures unbuffered standard output and standard error streams from the agent harness execution. It assists with post-mortem debugging whenever an execution hangs or crashes unexpectedly.
	\item \texttt{transcript.jsonl}: Stores the comprehensive turn-by-turn event stream, including internal reasoning traces, tool parameters, and raw tool responses. It provides full behavioral provenance for qualitative evaluation.
	\item \texttt{trial\_meta.json}: Records structured trial execution metrics, including pass/fail status, validation stages completed, latency, token usage, and dependency precision. It supplies the ground-truth values used to calculate Pass@$k$ and bloat statistics.
	\item \texttt{tool\_call\_frequency.csv}: Records the overall frequency, trial prevalence, and average invocations of every agent tool call. It quantifies how agent tool usage shifts between different model and grounding conditions.
	\item \texttt{tool\_call\_frequency\_by\_task.csv}: Cross-tabulates tool calls across individual coursework assignments. It reveals which problem domains provoked heavier tool utilization.
	\item \texttt{tool\_call\_frequency\_by\_trial.csv}: Maps tool invocations at the level of individual trial samples alongside validation success and duration. It facilitates fine-grained correlation between tool call patterns and task outcomes.
\end{itemize}

\subsection{Three-Stage Validation Pipeline and Pass@K Formulation}\label{subsec:pass-k-metric}

Synthesizing a declarative \texttt{flake.nix} file requires navigating a functional domain-specific language where surface syntactic correctness does not guarantee runtime deployability~\cite{zhangDeployabilityCentricInfrastructureasCodeGeneration2025}. To rigorously verify that generated environments are functional, every candidate flake must satisfy a three-stage automated validation pipeline:
\begin{enumerate}
	\item \textbf{Syntax and Evaluation Validity:} The command \texttt{nix flake check} evaluates the generated \texttt{flake.nix} with lock-file writes disabled, ensuring that the expression parses cleanly without syntax errors, missing attributes, or invalid type signatures.
	\item \textbf{Build and Realization Determinism:} The command \texttt{nix develop --command <test-cmd>} successfully enters the ephemeral shell and resolves all declared binaries on the \texttt{PATH}.
	\item \textbf{Functional Task Execution:} The assignment source code builds and passes its unit test suite inside the synthesized \texttt{devShell}, verifying that compiler toolchains and runtime headers interact correctly with project source files.
\end{enumerate}

To quantify synthesis reliability, we adapted the Pass@$k$ formulation from code generation literature~\cite{chenEvaluatingLargeLanguage2021}. Pass@$k$ measures the probability that at least one of $k$ generated candidate environments passes all validation stages, where we generate $n \ge k$ samples per task. For our evaluation, we set $k = 3$ and $n = 3$.

We use the unbiased estimator introduced by Chen et~al.~\cite{chenEvaluatingLargeLanguage2021}:
\[
	\mathrm{pass@}k := \underset{\text{Problems}}{\mathrm{E}} \left[ 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}} \right]
\]
where $n$ is the total number of generated candidate samples per task and $c$ is the number of samples that successfully pass all three validation stages.

\section{Clean-Environment Reproducibility Protocol}\label{sec:rq2-methodology}

RQ2 evaluates whether a successful local validation actually transfers to a fresh environment that has none of the authoring host's files, shell configuration, or prior evaluation state. The inputs contain only RQ1 trial artifacts that passed the three-stage local verifier and include both a generated \texttt{flake.nix} and its \texttt{flake.lock}. This design evaluates the reproducibility of the generated flake specification.

On a local development machine, an existing warmed Nix store or globally installed host library may mask missing dependency declarations, creating a false impression of reproducibility. To isolate the environment from authoring host pollution, our protocol mandates that candidate flakes be tested in fresh, ephemeral guest environments where no host directories or store paths are mounted.

The harness streams a compressed copy of the trial into the guest environment and extracts it into guest-local temporary storage; no project directory or host Nix store is mounted. The guest instance is discarded when the stage finishes, so no writable state is shared across stages or trials. Network access remains available so that a first-use environment can retrieve its pinned inputs and binary-cache artifacts, and availability failures are recorded separately from configuration failures.

\subsection{Guest Replay Pipeline and Failure Taxonomy}

The guest-side verifier executes four sequential stages on each RQ1-passing artifact:
\begin{enumerate}
	\item \textbf{Locked Flake Evaluation:} \texttt{nix flake check} evaluates the generated flake with lock-file writes disabled.
	\item \textbf{Development-Shell Activation:} \texttt{nix develop --command true} verifies that the development shell can be activated.
	\item \textbf{Required Tool Availability:} Each executable listed in the original RQ1 dependency assertion is checked with \texttt{command -v} inside the development shell.
	\item \textbf{Headless Task Execution:} A curated per-task command set verifies applicable language runtimes, builds, dependency synchronization, or test commands. Graphical editor workflows, interactive credentials, and persistent database-service administration are excluded because they cannot be assessed consistently by a headless guest.
\end{enumerate}

The principal metric is the base OS reproduction rate: the proportion trials that complete every applicable container-side stage. Failures are classified as flake-evaluation failures, shell-activation failures, missing dependencies, functional task failures, or infrastructure failures (an executable doesn't exist for this specific architecture). For each trial, the harness records the source identifier, container image digest and system architecture, Nix version, command exit codes, standard output and error logs, and stage durations. These artifacts make it possible to distinguish a defective generated environment from a transient container or upstream package-source failure.

\section{Student Onboarding Ergonomics Protocol}\label{sec:rq3-methodology}

RQ3 evaluates the practical ergonomics and setup time delta of Nix Flakes from a student perspective compared to traditional manual installation. To assess human ergonomics and onboarding friction, we conducted a controlled user study involving two undergraduate students and a graduate computer science student. Each participant was tasked with configuring a course development environment using two contrasting methods: traditional imperative instructions from a course document, and a \texttt{flake.nix} file that was generated with the above instruction guide.

Each trial was executed with 2 clones of a vanilla macOS virtual manager from Cirrus Labs, invoked via \texttt{tart run --dir=host:./ <student-A-dev>} where \texttt{--dir:} is the current directory of the AI generated flake. In the macOS VM, this becomes a shared volume, automatically providing the VM the required files.

We recorded total setup completion time, the time delta between imperative installation and declarative shell activation, the student's personal assessment of their preferred workflow, and qualitative observations regarding cognitive load.

We evaluated three progressively complex coursework environments to capture how setup time and procedural friction scale with dependency complexity. The first task required installing a single compiled language toolchain consisting of the Rust compiler and Cargo build system. The second task involved provisioning a data science environment with a Python runtime and the Jupyter Notebook package. Finally, the third task required configuring a multi-component full-stack web development environment integrating multiple language runtimes, package managers, and database utilities.

\chapter{Empirical Results and Analysis}\label{chap:results}

\section{Flake Synthesis Accuracy and Model Comparison}\label{sec:model-results}

Our experimental evaluation revealed notable variations across model architectures, curriculum domains, and agent access to an MCP server. In our initial evaluations conducted without the custom agent skill, general-purpose LLMs exhibited a strong tendency toward imperative fallbacks. Specifically, when operating on a macOS test host, models frequently attempted to install missing packages imperatively via Homebrew (\texttt{brew install}), failing to produce a declarative \texttt{flake.nix} file entirely, despite explicitly prompting the model.

With the introduction of the \texttt{course-flake-generator} skill, the model behaved more consistently. The agent successfully adhered to the declarative flake pattern for over 85\% of standard software development prompts. However, curriculum domain complexity strongly influenced outcomes. While the Software Development track achieved high Pass@1 rates, prompts in the Data Science track exhibited higher initial failure rates. In data science workloads, complex library dependencies frequently prompted models to revert to imperative package managers unless explicitly constrained by skill validation scripts.

Under the Pass@3 metric, Gemini~3.8 Flash succeeded on at least one attempt for every assignment prompt in the benchmark (100.00\% Pass@3), whereas GPT-OSS~120B achieved 78.57\% Pass@3 with MCP access and 85.71\% without MCP access. These results partially support Hypothesis~\textbf{H\textsubscript{1a}}: structured procedural scaffolding and closed-loop validation enabled both the frontier model and the smaller open-weight model to synthesize functional environments across the majority of coursework prompts, though a performance gap persisted between model tiers. As detailed in Section~\ref{sec:telemetry-analysis}, this residual gap stemmed primarily from differences in tool utilization: GPT-OSS~120B made significantly fewer calls to the MCP server and relied more heavily on its parametric weights, leading to higher initial hallucination rates for less common package attributes.

Table~\ref{tab:model-synthesis-results} summarizes the overall synthesis accuracy across both models with and without access to the \texttt{mcp-nixos} server, Table~\ref{tab:model-telemetry} reports mean trial duration and token consumption, and Table~\ref{tab:model-bloat} presents package precision and the over-provisioning (bloat) ratio across passing trials. To evaluate partial success, the evaluator extracts all package identifiers declared in \texttt{packages}, \texttt{buildInputs}, and \texttt{nativeBuildInputs} (exempting standard Nix formatters such as \texttt{nixfmt} or \texttt{alejandra} and flake scaffolding attributes) and maps them against the expected CLI tools for each task. \emph{Package precision} measures the fraction of declared packages that directly satisfy an expected tool requirement (penalizing unrequested, extraneous packages), whereas the \emph{over-provisioning ratio} (bloat) computes the ratio of total declared packages to the minimum number of required packages needed to cover the expected tools, capturing both extraneous additions and redundant package declarations.

\section{Tool Invocation and Telemetry Analysis}\label{sec:telemetry-analysis}

The tool-call logs were analyzed to determine how the agent resolved package and command uncertainty while constructing a flake. This analysis complements the pass/fail synthesis metric: a successful flake does not reveal whether the agent relied on parametric knowledge, live package retrieval, or native command-line inspection to reach the result. MCP-server availability was controlled by the experimental harness; it was not a tool-selection decision made by the model.

\subsection{Native Nix CLI Discovery versus MCP Retrieval}

Our baseline experiments evaluated whether an agent strictly requires the \texttt{mcp-nixos} server for successful synthesis. In our testing script, we added a flag to run a condition in which the MCP server was withheld from the model. Even without MCP access, the model produced valid environments across the benchmark by combining native Nix CLI discovery with its parametric knowledge of the Nixpkgs derivation schema. Guided by the skill's procedural directive to verify that every resolved package attribute evaluates cleanly prior to finalizing \texttt{flake.nix}, the agent followed a progressive resolution workflow across the trial transcripts.

First, when resolving a target requirement from the prompt, the agent invoked \texttt{nix search} (e.g., \texttt{nix search github:NixOS/nixpkgs/nixos-24.11 dotnet-sdk}) or \texttt{nix-env -qaP} to identify candidate attribute names. Second, because Nixpkgs frequently exposes both unversioned default aliases and version-pinned attributes (such as \texttt{dotnet-sdk} alongside \texttt{dotnet-sdk\_8} and \texttt{dotnet-sdk\_9}), the agent executed targeted \texttt{nix eval} expressions to disambiguate candidates before writing the flake. Specifically, even though the skill documentation did not supply a cheat sheet of derivation attributes, the model leveraged its pre-trained knowledge of Nix idioms to query \texttt{.name} and \texttt{.version} (e.g., \texttt{nix eval github:NixOS/nixpkgs/nixos-24.11\#dotnet-sdk.name} and \texttt{nix eval --expr 'with import <nixpkgs> \{\}; openjdk17.name'}) to confirm concrete upstream versions; \texttt{.passthru.home} and \texttt{.outPath} to resolve store paths for environment variables such as \texttt{JAVA\_HOME} and \texttt{DOTNET\_ROOT}; \texttt{builtins.attrNames} (e.g., \texttt{builtins.attrNames pkgs.vscode-extensions}) to enumerate nested extension sets and test \texttt{vscode-with-extensions.override} expressions; and \texttt{.meta.platforms}, \texttt{.meta.broken}, and \texttt{.meta.license} to diagnose macOS (\texttt{aarch64-darwin}) compatibility for packages such as \texttt{rstudio} and \texttt{mysql-workbench}. In this benchmark, the Nix CLI therefore served as an effective, self-describing retrieval and verification interface when the MCP layer was unavailable.

Our findings were similar to the findings of \cite{formentScaffoldingMattersMore2026}. The effect that MCP servers introduces when it comes to token usage is inconclusive. It varies between agent harness used and in the case of the agent harness that we used, querying an MCP server resulted in less tokens.

This result should not be interpreted as evidence that MCP retrieval is generally unnecessary. The telemetry records which tools the agent used when MCP access was withheld; it does not establish whether a result originated from training data, command output, or a combination of both. mcp-nixos MCP server is better suited for recently recently modified . In those conditions, the structured and current metadata exposed by \texttt{mcp-nixos} remains a useful capability for reducing package hallucination and configuration drift~\cite{borkLanguageServerProtocol2023,ImportingPhantomsMeasuring}. The present result instead bounds the claim: for straightforward requirements, the model could construct a working flake without MCP access.

When the \texttt{mcp-nixos} server was provided, the two models exhibited a stark divergence in MCP tool adoption, as summarized in Table~\ref{tab:mcp-invocation-comparison}. Gemini~3.8 Flash invoked \texttt{call\_mcp\_tool} 136 times across all 40 completed trials (100.00\% trial prevalence, averaging 3.40 MCP calls per trial and accounting for 8.41\% of its 1,617 total tool invocations). Furthermore, Gemini~3.8 Flash leveraged the full breadth of the \texttt{mcp-nixos} schema; combining package and program \texttt{search} queries, detailed \texttt{info} lookups, \texttt{channels} verification, and binary \texttt{cache} checks on \texttt{aarch64-darwin}. In contrast, GPT-OSS~120B invoked \texttt{call\_mcp\_tool} only 6 times across just 3 of 41 completed trials (7.32\% trial prevalence, averaging 0.15 MCP calls per trial, or 1.02\% of its 590 total tool calls). Although GPT-OSS~120B probed the MCP server via \texttt{list\_resources} in 24 trials (58.54\%), it bypassed \texttt{call\_mcp\_tool} in over 92\% of trials, restricting its 6 actual MCP queries to basic package searches (\texttt{clang}, \texttt{cmake}, \texttt{make}, \texttt{gnumake}, \texttt{dotnet-sdk}, and \texttt{mysql-workbench}) without ever invoking \texttt{info} or \texttt{cache} actions. This under-utilization directly contributed to GPT-OSS~120B's lower synthesis accuracy on data science tasks, where it relied on stale parametric knowledge and hallucinated deprecated or improperly cased attribute names (such as referencing the removed top-level \texttt{mysql} attribute instead of \texttt{mysql80}/\texttt{mysql84} and lowercase \texttt{r} instead of \texttt{R}).

Consequently, the agent inferred that no MCP capabilities were available and defaulted to its parametric weights and native shell commands.

\section{Base OS Reproducibility Results}\label{sec:base-os-results}

The base operating system replay evaluation investigated the cross-platform reproducibility of eligible artifacts that passed host-side validation during the RQ1 synthesis benchmark. Each passing \texttt{flake.nix} and corresponding lockfile was evaluated across two isolated, clean environments: disposable Linux Docker containers running on an unprivileged host architecture and clean macOS virtual machines managed via the Tart virtualization framework. Replay trials executed an automated five-stage verification pipeline matching the host harness: static flake syntax check (\texttt{flake\_check}), development shell realization and hook execution (\texttt{activation}), binary presence verification on \texttt{PATH} for every declared dependency (\texttt{missing\_dependency}), and headless task command verification (\texttt{task\_<index>}). Replay outcomes were systematically classified according to the taxonomy implemented in \texttt{replay\_clean\_docker.py}, separating packaging errors from runtime functional execution errors.

Figure~\ref{fig:rq2-linux-results} and Figure~\ref{fig:rq2-macos-results} present the clean replay outcomes across the Computer Science and Data Science curriculum tracks for Linux and macOS, respectively. Across both operating systems, the generated flakes demonstrated robust structural isolation: zero trials encountered \texttt{flake\_failure}, \texttt{activation\_failure}, or \texttt{missing\_dependency}. In every instance, the Nix evaluator built the requested development shell derivation, populated the store paths, executed shell hooks without fatal exit codes, and placed all required tool binaries on the active \texttt{PATH}. Nevertheless, a subset of trials experienced \texttt{functional\_failure}, wherein the environment successfully activated with all dependencies present, but task-specific headless test commands exited with non-zero status codes.

In the Linux container replay (Figure~\ref{fig:rq2-linux-results}), 34 of the 41 eligible trials reproduced successfully without manual intervention, achieving an overall clean reproduction rate of 82.9\%. Across curriculum tracks, the Computer Science track achieved an 83.3\% reproduction rate (25 reproduced, 5 functional failures out of 30 trials), while the Data Science track achieved an 81.8\% reproduction rate (9 reproduced, 2 functional failures out of 11 trials). In the clean macOS virtual machine replay (Figure~\ref{fig:rq2-macos-results}), 39 of the 41 eligible trials reproduced successfully, yielding a 95.1\% overall clean reproduction rate. Specifically, the Computer Science track attained 93.3\% reproducibility (28 reproduced, 2 functional failures out of 30 trials), while the Data Science track achieved 100.0\% reproducibility (11 reproduced, 0 functional failures out of 11 trials).

Detailed post-mortem analysis of the trial logs revealed that all seven Linux failures and both macOS failures stemmed from three distinct root causes within the \texttt{functional\_failure} classification:

\begin{enumerate}
	\item \textbf{Container Privilege Boundaries and Electron Headless Sandboxing:} In the Linux Docker replay environment, all trials for the code editor environment failed during the headless verification of Visual Studio Code (\texttt{code --version}). The containerized replay harness executed inside disposable, headless Docker containers operating under the superuser (\texttt{root}) account. Visual Studio Code, built on the Electron framework, enforces a strict sandboxing policy that rejects execution under root privileges in headless Linux environments without explicit runtime flags, terminating immediately with the diagnostic: \textit{"You are trying to start Visual Studio Code as a super user which isn't recommended. If this was intended, please add the argument --no-sandbox and specify an alternate user data directory using the --user-data-dir argument."} In contrast, local host verification executed under a standard unprivileged user account, allowing \texttt{code --version} to exit cleanly. Similarly, on the clean macOS Tart virtual machines, the evaluation runner operated under the unprivileged \texttt{admin} user, where Darwin application bundles do not enforce Linux-specific container sandbox restrictions; as a result, all corresponding trials reproduced cleanly on macOS.
	\item \textbf{Host State Pollution via Mutable Toolchain Shims:} Across both Linux and macOS, multiple trials failed during the compiler verification command (\texttt{rustc --version \&\& cargo --version}) for the Rust toolchain environment. When synthesizing the development environment from prompt instructions requiring \texttt{rustup}, the agent declared the Nixpkgs derivation \texttt{pkgs.rustup} in \texttt{buildInputs} rather than the standalone compiler derivations \texttt{pkgs.rustc} and \texttt{pkgs.cargo}. In Nixpkgs, the \texttt{rustup} package provides proxy shims for \texttt{rustc} and \texttt{cargo} that dynamically resolve to toolchains managed under the user's mutable home directory (\texttt{\$HOME/.rustup}). On the author's local workstation, a default stable toolchain was already cached in \texttt{\textasciitilde/.rustup}, masking the uninitialized state and permitting the shims to execute during local RQ1 validation. When deployed to pristine guest environments where \texttt{\$HOME/.rustup} was empty, calling \texttt{rustc} failed with the diagnostic: \textit{"error: rustup could not choose a version of rustc to run, because one wasn't specified explicitly, and no default is configured."} In contrast, one synthesized trial succeeded on both Linux and macOS because the model included \texttt{rustup default stable} inside the flake's \texttt{shellHook}, dynamically bootstrapping the toolchain into the clean environment prior to command verification.
	\item \textbf{Absence of Display Server for Graphical Applications:} In the Data Science track, trials for the database administration environment failed during the verification command (\texttt{mysql-workbench --version}) during Linux container replay. MySQL Workbench is a desktop client application compiled against GTK and X11 graphical libraries. When invoked inside the minimal headless Docker container, the binary attempted to initialize a connection to a non-existent graphical display server, terminating with the runtime fault: \textit{"(mysql-workbench-bin): Gtk-WARNING **: cannot open display:"}. On the authoring host workstation, an active display server session was accessible. In the macOS virtual machine environment, Darwin application binaries and command wrappers do not depend on an X11 display socket, allowing all corresponding trials to execute without failure.
\end{enumerate}

These findings provide strong empirical validation for Hypothesis~\textbf{H\textsubscript{2}}, demonstrating that declarative Nix Flakes deliver high cross-platform determinism (95.1\% on macOS and 82.9\% on Linux) with zero environment-realization or missing-dependency failures. Crucially, the diagnostic failure taxonomy reveals an important distinction between \textit{infrastructure-induced evaluation artifacts} and \textit{authentic specification defects}. Five of the seven observed failures on Linux, specifically those involving graphical applications, were artifacts of the headless container test harness running under superuser privileges and lacking an X11 display server. Because student devices operate in unprivileged user accounts with graphical capabilities, these container-specific execution constraints do not impact practical student onboarding. Conversely, the failures observed during the Rust toolchain replay represent genuine specification defects resulting from host-state leakage, wherein mutable toolchain shims silently relied on ambient host caches. This underscores that clean-room replay in pristine guest environments is indispensable for validating that generated development flakes achieve true hermetic isolation.

\subsubsection{Student A}
During the imperative installation trial, Student~A completed the setup in 3~minutes and 21.22~seconds, but encountered multiple points of procedural friction along the way. Most notably, Student~A initially assumed that the leading shell prompt symbol (\texttt{\$}) printed in the documentation was a literal part of the command string to be executed. Furthermore, Student~A overlooked a critical post-installation instruction requiring them to source the Cargo environment script (\texttt{source "\$HOME/.cargo/env"}), which caused subsequent verification commands (\texttt{rustc --version} and \texttt{cargo --version}) to fail with command-not-found errors and created confusion regarding whether the compiler had actually been installed. This observation highlights a fundamental vulnerability of imperative installation guides: because manual procedures consist of stateful, sequential steps, inadvertently skipping a single environment-configuration step silently breaks downstream verification even when the underlying binaries have been downloaded successfully.

In the declarative Nix Flake trial, Student~A completed the setup in 4~minutes and 54.86~seconds, representing an additional 1~minute and 33.64~seconds compared to the imperative workflow. The majority of the time was spent waiting for the one-time installation of the Nix package manager itself and the initial realization of the development shell via \texttt{nix develop}. Despite the longer total wait time, Student~A expressed a clear preference for the declarative Nix Flake method, noting that once Nix was installed, activating the environment required a single deterministic command.

\subsubsection{Student B}
During the imperative installation trial, Student~B required 5~minutes and 19.95~seconds to complete the Rust setup. Throughout the process, Student~B reported feeling overwhelmed by the dense terminal output emitted by the \texttt{rustup} installer and consequently skimmed past the post-installation instructions printed to the console. As a result, Student~B failed to restart the terminal session or reload the shell configuration as instructed by the installer output, and expressed confusion when presented with system-specific explanations regarding \texttt{PATH} environment variable exports and shell profile files.

In the declarative Nix Flake trial, Student~B completed the environment setup in 7~minutes and 6.64~seconds, an increase of 1~minute and 46.69~seconds over the imperative trial due to the initial Nix installer and \texttt{devShell} realization overhead. Unlike Student~A, however, Student~B preferred the traditional imperative installation method for this single-toolchain task, explaining that the conventional step-by-step installer instructions felt more familiar and conceptually easier to follow than the unfamiliar Nix workflow.
